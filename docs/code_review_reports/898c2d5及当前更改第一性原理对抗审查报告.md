## 3. 第一性原理判据

### 3.1 最小事实所有权

| 事实或对象 | 应有权威来源 | 审查问题 |
| --- | --- | --- |
| Session、Message、AgentState、恢复状态 | AgentScope | API/前端投影是否丢掉关联，或自行制造终态？ |
| Harness 内容、候选、精确测试版本与发布版本 | Git 与受控发布记录 | 是否有普通操作直接改变活动指针？ |
| 用户运行意图、审批、反馈来源、版本绑定 | AgentGov | `run_id` 与稳定操作身份是否在失败/重试中仍可追踪？ |
| 原生回复 | AgentScope `reply_id` | 是否拿当前 run 的映射覆盖整段会话历史？ |
| 语义轨迹 | Langfuse，AgentGov 保留引用 | Trace 关联能否跨刷新与多轮保存，原文是否越界持久化？ |
| 文件授权 | 已发布 Harness、当前 run 授权及 OS 隔离 | 所有校验是否针对同一个实际目标？ |
| 可部署产物 | 固定源码、构建输入、镜像内容、所选配置 | 本机脚本成功是否能推出目标机独立执行成功？ |

`run_id`、`session_id`、`reply_id` 和 `trace_id` 不是应被简单合并的重复 ID：它们对应不同生命周期。问题在于能否维护可信关联，而不是 ID 数量。

### 3.2 对架构的双向检验

支持当前方向的最强理由：复用 AgentScope 的会话与执行事实，可避免第二套 agent loop；Git 的精确版本和不可变 Runtime Agent 绑定，能够让测试、发布、运行与反馈引用同一份 Harness。

反对当前落地方式的最强理由：如果“当前版本”仍由可被导出等旁路推进的工作目录 HEAD 决定，不可变 Runtime 绑定只是局部成立；如果前端每轮用不完整映射重建全会话，事实源集中也不能保证用户看到可信事实。大量防护脚本同样不能替代跨环境可执行性。

裁决：保留单一 Runtime 与薄控制面的方向；优先修复授权目标规范化、活动版本副作用、全会话关联和恢复监控。没有证据支持因此重新引入双 Runtime、消息正文镜像或长期 fallback。

## 4. 已确认发现

### R-01 / P1：静态文件规则必须以与执行一致的目标路径判定

**位置：** [policy_middleware.py](../../agentscope_runtime/policy_middleware.py) 的 `on_check_permission`（133、160、165 行）、`_matches`（390–401 行）、`_matching_rule`（403–412 行），以及已经做规范化的 `_bounded_run_rule_matches`（438–459 行）。

**触发条件：** Harness 对同一可写输出树配置较宽的 ALLOW，同时对其子目录配置更窄的 DENY 或 ASK。调用参数使用含父目录段等可归一到相同目标的路径形式。普通已发布 Harness 可以表达这种规则组合，规则冲突校验只拒绝完全相同的条目。

**证据：** 保护路径/可写根检查使用解析后的目标；静态 allow/ask/deny 却把原始 `tool_input` 交给 `tool.match_rule()`。本地固定 AgentScope 2.0.8 的 `Write`、`Edit` 实现对原始 `file_path` 做 `fnmatch`。只读实验比较了指向同一测试目标的两个字符串：

| 输入形式 | 规范化后相同目标 | 宽规则命中 | 窄规则命中 |
| --- | --- | --- | --- |
| 规范路径 | 是 | 是 | 是 |
| 含父目录段的等价路径 | 是 | 是 | 否 |

因此相同实际目标可得到不同权限判断：窄 DENY/ASK 未命中后落到宽 ALLOW。当前 run-scoped 授权已拒绝父目录段并生成规范路径候选，静态规则没有复用该边界。目标提交也把静态 DENY 交给原始字符串匹配；ASK 是当前扩展出的相同风险。

**影响和边界：** 影响可写树内部细粒度拒绝与人工确认；没有据此声称可写入任意宿主路径，也没有证明能突破独立的不可变 Harness/OS 沙箱边界。只读匹配实验未执行文件写入。安全并行审查受到工具内容审查中断，本项正式结论仅采用主审重新确认的源码与只读实验，不将未完成交付视为完整动态安全验收。

**修复方向：** 在策略入口统一文件目标的规范化/拒绝规则，再以一致语义执行 allow/ask/deny 和 run-scoped 判定；同步 worker 文件规则。补充同一目标的规范路径、相对/绝对形式、父目录段与链接形式的决策一致性测试。仅在单一分支增加一次字符串检查不足以闭合此问题。

### R-02 / P1：Workspace 导出不能隐式推进活动 Git HEAD

**位置：** [agent_workspace_packages.py](../../app/services/agent_workspace_packages.py) `export_workspace` 第 99–130 行，特别是第 117 行；[agent_workspace_git_operations.py](../../app/services/agent_workspace_git_operations.py) 第 62–82 行；[provisioning.py](../../app/runtime_gateway/provisioning.py) 第 616–626、758–780 行。

**触发条件：** 已注册 Agent 没有未完成变更集，活动 Workspace 存在可归档的未提交变化，用户调用 `POST /api/agent-registry/{agent_id}/workspace/export`。

**证据链：** export → `snapshot_live_workspace` → `git add -A -f` → `git commit` → 成功时保留新 HEAD。只有导出失败才撤回快照。此路径不执行候选测试、审批或 Runtime 发布激活。与此同时，`_current_version_source()` 直接用 `inspect_clean_head()` 返回的 HEAD 和当前目录 digest 查找 Runtime 绑定。

现有测试 [test_agent_workspace_package_operations.py](../../tests/test_agent_workspace_package_operations.py) 第 336–354 行，在临时 Agent 中删除除 `.git` 外全部文件，随后断言：导出 HTTP 200、HEAD 已变化、HEAD 文件树为空。本轮执行该用例得到 **1 passed**，证明测试固化了旧操作语义，而不是证明新发布不变量成立。

**影响和边界：** 导出改变活动版本事实，却没有创建对应的 Runtime 版本绑定；有效 Harness 被修改后新 tuple 查不到绑定，`current()` 返回 `None`。完全删除 Harness 的情形还会使后续读取 manifest 失败。这不意味着所有旧 Session 都立刻失效：旧 Session 有自己的不可变绑定，本轮没有做真实旧会话验证。

**提交归属：** 导出快照行为在目标提交存在；原实现可有独立历史理由，但与本提交引入的不可变 Runtime 绑定以及当前候选发布单轨发生冲突。当前已移除其他直接改写入口，仍留下此处活动写入。

**修复方向：** 导出指定已发布 commit；若产品必须导出未提交内容，在隔离位置形成导出快照并明确其非发布状态，不能推进活动 HEAD。将现有“导出成功推进 HEAD”测试替换为“导出不改变活动 commit/Runtime tuple”，另测失败后 dirty/index 状态保持。

### R-03 / P1：远程独立预检依赖新模块，阻断旧版本升级

**位置：** [deploy_agent_gov_to_host](../../scripts/deploy_agent_gov_to_host) 第 212–225 行；[agentscope_atomic_cutover.py](../../scripts/agentscope_atomic_cutover.py) 第 20、29–33 行。

**触发条件：** 目标机已有 `docker/.env`，部署脚本在同步新源码前执行远程 schema 预检；目标机源码仍为 `898c2d5` 或更早状态。

**证据链：** rsync 此时只传送 `.agentscope_atomic_cutover.preflight.py`；新预检脚本在模块顶层导入 `app.runtime.sqlite_schema_contract`，但该模块属于当前未跟踪新增文件。它尚未传输，目标提交也没有该模块。新脚本还新增 `python-dotenv` 的启动依赖，破坏原先独立脚本边界。

本轮用临时旧目录、当前预检文件和本地已具备依赖的解释器执行，即使只调用 `--help`，仍返回 1：`ModuleNotFoundError: No module named 'app.runtime.sqlite_schema_contract'`。现有 `test_standalone_remote_preflight_inspect_remains_read_only_and_self_contained` 同样失败，报缺少 `app`。

**影响：** 在读取数据库之前阻断正常远程升级；属于可用性回归，未证明造成数据破坏。主源码同步位于预检之后，不能靠“随后 rsync 会带上文件”解决。

**修复方向：** 将预检所需固定版本模块及依赖作为自包含只读包一并传输，或保留可独立运行的预检实现并由共享生成物约束其一致性。必须用没有新源码、没有仓库 `PYTHONPATH` 的目标目录跑实际子进程测试，不能仅检查脚本包含预检命令。

### R-04 / P2：每轮只带当前 run 的全会话重投影会清除历史关联

**位置：** [playgroundRunHelpers.ts](../../frontend/src/playgroundRunHelpers.ts) 第 203–211 行；[usePlaygroundRun.ts](../../frontend/src/hooks/usePlaygroundRun.ts) 第 460–472 行；[playgroundHistory.ts](../../frontend/src/playgroundHistory.ts) 第 75–104 行。

**触发条件：** 同一 Session 连续完成两轮，原生 Message 没有 AgentGov `run_id` metadata。这是正常情形：原生回复 ID 通过 AgentGov `reply_ids` 关联 run；当前 `/chat/` 请求并不写入消息级 run metadata。

**证据：** 终态读取整个 Session 的 canonical messages，却仅把 `[run]` 传给 `messagesFromAgentScopeMessages()`；其结果替换整个 Session。`mergeExactRunEventsIntoCanonicalMessages()` 又只保留当前 run 的事件，不保留旧消息已经确认的治理上下文。

真实函数实验结果：第一轮原有 `runId=run-1`、`traceId=trace-run-1`、事件数 1；第二轮完成后同一 `reply-1` 的 run/Trace 字段均消失、事件数变成 0，只有第二轮仍关联 `run-2`。

**影响：** 历史回复的 Trace 入口和精确反馈来源丢失。普通列表刷新不能保证补回：现有会话已含消息时，App 会跳过 history reload。原生文本仍然存在，不能把本项描述成 AgentScope 删除了消息。

**修复方向：** 保持 canonical 文本来源，同时使用全会话 run 映射，或按稳定 Message ID 合并已验证的历史治理关联。补两轮完成后旧回复仍能查看正确 Trace、提交精确 run 反馈的行为测试。目标提交已有相同的 `[run]` 全量替换问题。

### R-05 / P2：正文与错误并存时，canonical 错误详情被丢弃

**位置：** [playgroundHistory.ts](../../frontend/src/playgroundHistory.ts) 第 38–52 行，核心是 `content: content || fallback`。

**触发条件：** 原生 Message 有非空部分正文，`finished_reason` 为 error，同时带有具体 `error.message`。

**证据：** `terminalFallback()` 读到错误后，因为正文非空而被忽略；生成的 ChatMessage 没有独立错误字段。以合成正文 `partial output` 和错误 `specific failure details` 调用真实投影函数，结果保留正文、`runOutcome=failed`、`partial=true`，却完全不包含错误详情。

**影响：** 用户只能看到失败/部分输出标签，无法获知失败原因；历史重新加载仍经过相同投影。即时 SSE 事件偶尔含错误不能替代 canonical 恢复路径。目标提交已有相同表达式；现有测试只覆盖 error-only，不覆盖正文与错误同时存在。

**修复方向：** 将正文和结构化错误分开投影与展示，同时处理空正文、部分正文、历史加载和终态合并。保留错误源与重试入口，不用追加一段无法区分的错误文本污染模型正文。

### R-06 / P2：恢复出 run 身份后，快照失败不能停止终态监控

**位置：** [playgroundRunRecovery.ts](../../frontend/src/playgroundRunRecovery.ts) 第 45–71 行。

**触发链：** 初始 POST 已提交但响应丢失 → `by-client-operation` 找回精确 run → `bindRunHandle()` 成功 → 第一次 `loadSnapshot()` 临时失败 → catch 只写 `reconciling` 错误然后返回。`ensureTerminalMonitor()` 在快照成功之后，因而没有启动。

**证据：** 使用真实 recovery/API request 代码和临时 loopback HTTP fixture，操作查询返回 run-1，随后 messages/status 恢复返回错误。实验得到 `boundRun=run-1`、`monitorCount=0`、`reconnectCount=0`，最后状态为 reconciling。

**影响和边界：** 在这一特定入口，后端后来成功也不会自动使前端收敛，用户需要整页刷新或再次触发停止恢复。不是所有网络故障都会发生：正常成功 POST 路径已经启动监控，因此问题应限定在初始回执丢失后的首次恢复链。

**修复方向：** 精确恢复 run ID 后立即建立持续终态监控；将消息快照失败作为展示恢复问题，采用可取消、带退避的重试。测试必须覆盖“第一次网络失败后又发生第二次失败”，而不仅是 operation lookup 后立即恢复成功。

### 10.2 已确认的文档治理发现

#### D-01：当前实现基线与代码的数据库版本不一致

**证据：** [Runtime 替换基线](../engineering/AgentGov_AgentScope_Runtime替换实施基线与验收.md) 第 71、128–134 行仍声明当前 epoch 为 v2，并以 v1→v2 解释普通部署迁移；[整改实施记录](../engineering/AgentScope_API最大复用与单轨整改计划.md) 第 226、258 行也保留 v2 口径。当前 [sqlite_schema_contract.py](../../app/runtime/sqlite_schema_contract.py) 第 66 行已声明 `CURRENT_SCHEMA_EPOCH = "agentscope-runtime-v3"`，[runtime_db.py](../../app/runtime/runtime_db.py) 引用这一集中常量。

**影响：** 部署、迁移和故障判断可能按旧数据库边界执行。同一易变契约同时维护于 README、基线和实施记录，扩大了同步范围。并发开发可解释短时漂移，但不能将这些正文作为与当前代码一致的已核定依据。

**建议动作：** `keep` 基线和实施记录；当前 epoch、支持的源 schema 和迁移条件指定一个详细正文归属，其他文档保留摘要与引用。实施记录中的历史迁移必须标明发生时版本，不继续写成“当前”。

#### D-02：术语权威与活跃索引对旧 API 名称给出相反许可

**证据：** [术语与版本边界](../AgentGov术语与版本边界.md) 第 104 行将 `proposal` 描述为当前方案生成 job 的输出命名，并允许当前代码/API 名保留；[文档索引](../README.md) 第 68 行却要求它只作为迁移来源或归档证据，不能作为当前 API/UI 主流程依据。[反馈基线](../反馈闭环当前实现基线.md) 第 11–24 行已使用 `OptimizationPlan` 解释当前四阶段。

**影响：** 开发者和 Agent 可以从不同权威文档得出相反实施要求，旧契约可能据此被错误保留或重新引入。

**建议动作：** `keep` 术语文档并修订过时许可，明确“旧名称的历史解释”与“允许继续存在的公开契约”。索引只描述角色和指向关系，避免另外维护一套相反的术语规则。

#### D-03：规划文档转为实施记录后，旧问题仍标作当前事实

**证据：** [整改实施记录](../engineering/AgentScope_API最大复用与单轨整改计划.md) 第 3、7 行声明 P0–P4 已实施、本文已由规划转为实施与验收记录；第 57–75 行“当前事实与整改对象”仍列已删除的 `app/routers/catalog.py`、`app/runtime/agent_loader.py`、`app/runtime/config_mapping.py` 和 `app/services/agent_config_files.py`。其中第 67 行仍把上游 Session 类型描述为手写协议，但当前 [runtime.ts](../../frontend/src/types/runtime.ts) 已从 `AgentScopeComponents` 派生对应类型。

**影响：** 读者无法判断列出的内容是整改前问题、尚未完成的缺口，还是已完成事项；仅修改标题和顶部状态不能完成文档生命周期转换。

**建议动作：** `split` 文档内的语义角色：原始问题保留为带日期或提交边界的“整改前证据”，当前实现与剩余验收分别记录。已由基线承载的当前契约改为引用，避免整篇实施记录成为第二份基线。

#### D-04：已退出的阶段仍参与当前依赖与评审指令

**证据：** [下一阶段实施方案索引](../AgentGov下一阶段实施方案索引.md) 第 119–120 行明确旧 P0 不再作为当前依赖，但第 105–109 行依赖图和第 248–249 行评审清单仍保留历史 P0；第 142–144 行还把历史 Claude capability tuple 列作“已选实施裁决”。

**影响：** 旧方案虽然移入归档，其约束仍能通过活跃索引影响执行顺序和验收判断。本项针对仍生效的指令位置，不针对有明确时间边界的历史证据。

**建议动作：** `keep` 阶段索引，当前依赖统一到现行 Gateway 与质量准入条件；旧 P0、Claude tuple 只保留历史说明和归档引用。修正文内依赖图、裁决与评审清单，不只改一段退出声明。

#### D-05：治理规则自身把当前基线误定义为迁移前事实

**证据：** [文档治理策略](../文档治理与归档策略.md) 第 31 行要求当前实现基线中的真实 API、数据库、测试和 UI 名称声明为“迁移前事实”；但同文第 43 行要求基线给出当前代码或运行态证据，[文档索引](../README.md) 第 18 行及[反馈基线](../反馈闭环当前实现基线.md) 第 3 行也明确基线解释当前事实。

**影响：** 按治理规则执行反而可能把真实当前契约标成历史，使文档角色和权威优先级失去可解释性。

**建议动作：** `keep` 治理策略，仅历史名称和已替代实现要求标注迁移来源；当前基线、目标方案、迁移前历史分别定义，不把当前基线统称迁移前。

#### D-06：Workspace 测试工程契约重复维护并出现语义差异

**证据：** [四阶段 UI 方案](../AgentGov_四阶段改进治理工作台UI整改方案.md) 第 676 行泛称每个测试函数独立创建和关闭会话；[pytest 工程方案](../engineering/业务AgentWorkspace原生pytest测试资产实现方案.md) 第 102 行则区分：`agent` fixture 管理会话，直接 `invoke_agent` 需要显式会话 ID。UI 方案第 13 节、反馈基线第 82–133 行和 pytest 工程方案还分别维护 testkit、runner、生命周期和发布条件。

**影响：** 读者可能误以为任何测试函数都自动获得隔离会话；同一工程契约在多个角色文档中维护，增加漂移和修订成本。

**建议动作：** `merge` 工程细节到 pytest 工程方案；UI 方案保留用户交互、结果展示及错误入口，反馈基线保留已实现摘要和链接。跨文档重复的简短边界说明可以保留，不要求机械消除所有重复句子。

### 10.3 检查能力与未确认问题

[文档检查器](../../scripts/check_docs_governance.py) 第 137–156 行通过路径字符串和归档列名检查索引；第 159–172 行跳过页内锚点，并只取跨文件链接的 path 部分；当前链接正则不覆盖引用式链接。归档检查没有逐行验证替代文档、日期和完整替代链。第 278 行的术语检查只覆盖指定文档和少数旧治理 Agent 名称，不能发现 D-02 的权威冲突。

这些是能力边界，不能据此声称已经发现断链或所有归档关系无效。此前抽查的三个显式章节锚点均对应真实标题；D-01 至 D-06 则有正文或代码反证，属于已确认内容问题。文档体积、文档年龄、含有历史名词或缺少统一 front matter，均未被单独计作缺陷。

### 10.4 建议顺序与验收

1. **先统一当前口径。** 处理 epoch、旧术语许可、当前基线角色和已退出阶段依赖；逐项记录事实归属与受影响文档。
2. **再收敛重复正文。** 易变运行与迁移契约、pytest runner 细节分别由一个正文承载；计划转换为实施记录时同步划分历史、当前和剩余验收。
3. **最后补必要检查。** 保留现有轻量结构门，对锚点、明确替代关系及可派生契约增加适量核验；不以新增复杂文档平台或继续叠加词语禁令替代内容修订。

完成标准是：同一问题从索引、权威正文和代码得到一致结论；历史材料有明确边界，当前指令不依赖已退出阶段；目标、实现和真实验收分别有依据。核验仍包含文档检查、术语检查和差异检查，完整 `make codex-guard` 的源码阻断需单独如实记录。本文只纳入审查结果，未实施 D-01 至 D-06 的整改，也未归档、删除或移动被审查文档。
