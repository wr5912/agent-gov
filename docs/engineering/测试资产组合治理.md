# 测试资产组合治理

## 目标与边界

测试治理的目标不是减少测试数量，而是用更低的执行与维护成本持续获得可信、及时、可定位的质量反馈。`tests/quality_policy.json` 是机器可读的单一入口；本文解释稳定工程契约，不复制具体 nodeid 清单。

覆盖率只证明代码被执行过，不单独证明缺陷检测能力。组合决策同时考虑：

- **Speed**：目标测试与完整测试的 p50、p95。
- **Maintainability**：重复断言、实现细节耦合和 owner 缺失。
- **Utilization**：runner 时间、CPU 分钟、容器和模型资源。
- **Reliability**：flaky、重跑后通过、隔离时长和证据完整性。
- **Fidelity**：组件、契约、浏览器、真实容器和 live 模型的生产接近度。

## 资产模型

每个 pytest 叶子 nodeid 必须且只能得到一个有效分类。策略用文件 glob 建立基础分类，参数化用例在真实 pytest collection 后展开；规则零匹配、重叠或漏分类均阻断治理门。

分类同时包含：

| 维度 | 值 |
| --- | --- |
| 执行层级 | static、unit、component、contract、integration、e2e、performance、security、resilience |
| 保护目的 | requirement-regression、defect-regression、security-boundary、compatibility-migration、data-integrity、architecture-contract、implementation-detail |
| 生命周期 | KEEP、PROMOTE、DEMOTE、REFACTOR、MERGE、QUARANTINE、DELETE-CANDIDATE |
| 运行约束 | owner、capabilities（可多值）、lanes、parallelism、非空 resource classes |

逻辑 owner 以业务域登记，联系人可以暂时相同，但责任边界不能退化为文件作者。当前域包括 runtime-platform、improvement-governance、agent-lifecycle、security-response、frontend-experience、engineering-governance 和 integrations。

`QUARANTINE` 必须有 owner、原因、issue、隔离日期、到期日和修复方案，最长 14 天。`DELETE-CANDIDATE` 至少需要两类证据，例如业务路径已删除且有更强替代测试。没有可执行测试的重要风险登记为 `GAP`，不能用永久 skip 或无断言测试伪装资产。

### 业务 Agent Workspace 测试

平台测试与 Workspace 自有测试按维护责任和发布对象分开治理：

- 根目录 `tests/` 验证 AgentGov 平台代码、API、迁移、UI 和部署契约；
- 每个业务 Agent 的 `workspace/tests/` 验证该 Agent 的行为和工具集，由 Workspace 开发者维护并随其 Git 版本发布；
- `packages/agentgov-testkit` 提供远程调用和 pytest fixture，平台用固定命令执行指定业务 Agent commit；
- 仓库初始化源和 `${HOME}/volume-agent-gov` 中的业务 Agent 自测均不进入系统静态收集，其测试按该 Agent 的精确 Git commit 独立执行；
- 业务 Agent 发布运行完整 `workspace/tests/`，不只运行本次变更涉及的用例；已有失败与新增失败都阻断反馈闭环版本发布；
- governor Workspace 自测由平台团队维护，进入系统质量策略，但不注册为业务 Agent，也不进入业务发布条件判断。

业务 Agent 测试资产、运行状态、导入规则和发布条件以
[业务 Agent Workspace 原生 pytest 测试资产实现方案](./业务AgentWorkspace原生pytest测试资产实现方案.md) 为准。
平台不得把 Workspace 测试复制成数据库测试集或通用 Registry 资产。

### 发布评测包

业务 Agent Workspace 测试与平台发布评测包按信任域继续分开：

- Workspace 测试由 Agent 所有，承担可见工程契约和已知问题回归；
- 正式发布评测协议、评分器和 holdout 由独立评测 owner 在候选不可修改的版本化资产中维护；
- 平台 runner 可以复用 `AgentTestRun` 执行适配能力，但必须把精确 Agent commit、protocol revision、
  corpus/scorer digest、Runtime/模型/工具/环境 provenance 和结果用途绑定为 typed 证据；
- 数据库和通用 Registry 只保存引用、digest、执行结果与关系，不复制 Workspace 或评测包正文；
- 出现第二协议、动态环境、人工 review 或跨 Agent campaign 时，评测执行升级为独立领域入口，
  不继续扩宽 pytest report 充当全部评测模型。

同一候选不能同时修改被测行为和决定正式发布基准。评测基准变更必须独立评审，历史结果只有在
协议和环境兼容时才允许比较。

## 执行通道

| 通道 | 当前职责 | 门禁 |
| --- | --- | --- |
| `make codex-guard` | Codex/docs/OpenAPI/版本治理与测试策略检查 | 非琐碎改动必跑 |
| main-full | 全量离线后端、coverage、JUnit 与证据包 | 提交和发版前必跑 |
| main-flow | 产品主流程绑定的后端与 hermetic UI 自动化回归 | 主流程改动必跑；不作为真实部署验收证据 |
| impact shadow | Test Impact Analysis 选择结果与全量结果配对 | 仅本地评估，不替代全量 |
| parallel shadow | n2/n4、load/worksteal 与串行结果配对 | 仅本地评估，不替代串行 |
| mutation | 高风险状态机的限时 mutation score | 人工按风险执行 |
| container-core-acceptance | 一次 Compose 刷新后的 readiness、UI 首页、OpenAPI 只读检查 | 使用 `make container-core-smoke` |
| container-isolated-acceptance | 真实 Compose、模型、AgentScope Runtime 与 UI 验收 | 只通过公开 Make 入口在临时项目中执行 |

`make main-flow-test` 同时执行绑定的后端与 hermetic UI 回归。`main-flow-ui-test` 只是该 UI 子通道，不能单独宣称主流程或真实验收通过。需要真实容器 UI 时单独执行 `make main-flow-live-test`；它使用仓库外人工复核场景，只刷新一次隔离 Compose 栈，再串行执行 Playground 取消与改进闭环 UI。提交由操作者在本地执行串行 `make test`；部署前再按风险追加真实容器验收。

test double 按证据用途治理，不对普通测试一刀切。`tests/quality_policy.json` 的
`test_evidence.fault_injection_selectors` 声明单元/组件故障注入资产；这些测试可以在最小生产边界上使用
`monkeypatch`、受控 transport/provider、fake clock 或 hostile formatter 输出，以稳定触发并发竞争、响应丢失、
Git/DB 部分提交、补偿失败、恶意输入和不可达异常分支。替身必须局限于被注入边界，不得把预置结果描述为真实
Runtime、live provider、业务效果或端到端验收证据。

`test_evidence.formal_live_selectors` 与 `formal_live_targets` 才是正式 live/e2e/容器验收边界。这些文件和
Make target 禁止 `unittest.mock`、pytest `monkeypatch`、`MockTransport`、Vitest/Node mock、fake timer、
HTTP test-double library、Playwright 请求/HAR 重放、合成 DOM/启动状态、合成
API/SSE/Runtime/trace/provider 响应以及 no-op 子命令。`make test-double-check` 从策略读取边界，
并递归扫描正式资产导入的仓库内 Python/JavaScript 依赖；`make codex-guard` 对未匹配
selector、缺失 Make target 和命中违规 fail closed，不扫描普通 `tests/` 或 frontend unit
作为正式验收。

反馈闭环动态生成或导入的 Workspace suite 同样属于发布证据边界，但它不是仓库静态 selector：生产 AST
策略在生成、suite 检查和精确 checkout 后三处拒绝 mock/patch、fixture/plugin/hook 覆盖、符号链接、
`agent.run` 替换与 result 篡改；pytest 以隔离模式运行并禁自动插件。最终 invocation 只接受 API 服务端
绑定到当前 `test_run_id` 的证明，不接受 pytest 子进程自报内容。正式 Make 入口的 runner、Python、递归
Make 与容器验收命令变量使用 `override`，静态策略也拒绝验收资产尝试覆盖这些变量。

| 证据类型 | 可使用的机制 | 可以证明 | 不得宣称 |
| --- | --- | --- | --- |
| unit/component fault injection | 局部 test double、真实临时 SQLite/Git/文件系统、生产 store/router | 确定性负向语义、补偿、幂等和安全边界 | live Runtime、跨进程可靠性、业务效果 |
| formal live/e2e/container | 当前工作树镜像、真实服务、公共 API、真实浏览器/provider | 对应声明场景的运行态链路 | 未执行能力、未审输入或长期稳定性 |

通过生产构造器执行的真实 ASGI 应用和回环 HTTP 可以提高组件保真度，但只有策略声明的正式容器入口才能产生 live
证据。决策依据是：全局禁用替身会删除最关键且难以稳定复现的恶意、并发与部分失败回归；仅以真实环境制造全部故障
既不确定也可能破坏宿主资源，因此不采用。若未来某类故障能由隔离、可重复且成本可控的真实进程注入覆盖，可将对应
组件测试升级或去重，但必须先保留等价负向断言和历史缺陷保护。

隔离真实容器验收入口持有统一锁，基于当前工作树重建本地镜像（可复用 Docker build cache，不拉取远端代码）。所选完整 Compose env 只提供 secret 和非宿主配置；runner 为每轮生成临时 Runtime 根、唯一 Compose project/容器前缀、随机回环端口，并覆盖全部 `HOST_*_MOUNT` 与 Langfuse 数据挂载。它只在该临时项目中 `--force-recreate` 服务并验证镜像/容器 run id 与工作树摘要，无论成功失败都 `down --volumes` 后删除临时目录，不读写既有 `${HOME}/volume-agent-gov`。单个公开目标每次都会重新刷新；批量 core 检查使用 `make container-core-smoke`，只在一次刷新完成后把三个无写副作用的 HTTP 检查最多三路并行。Compose build/recreate、真实浏览器、live provider、Langfuse、共享 artifact 和 `main-full` 保持串行；TIA/xdist 达到策略规定的配对样本和时间窗前仍只作 shadow。

现场部署验收是另一类显式入口：`REQUIRE_LIVE_RUNTIME=1 make ui-playground-deployed-smoke`。
前置条件是人工维护窗口内停止发起新操作；部署锁不封闭 API 入站，只读在途检查不等于原子排空。
它复用 selected-env 部署事务，冻结所选完整 env、当前源码和工具链，在途任务不为空时拒绝重建；
构建并 `--force-recreate` **既有项目**，保留真实运行卷和身份。随后通过该项目的公开 UI/API，
使用已发布业务 Agent 完成 Chromium、Firefox 各一次两轮对话、精确 run 终态与刷新恢复验证。
本次验收 Session 保留供现场复核，不删除用户数据；仓库外私有报告仅存标识、长度、摘要及状态，
不存原始消息、工具参数、截图或 HAR。入口与浏览器脚本同样进入 no-test-double 静态扫描；不得
将它加入隔离 runner 白名单或伪造隔离上下文。其源码/env/镜像/容器身份必须通过前后复验。
该入口解决“隔离栈通过却不知道正式端口是否更新”的证据缺口，不替代隔离测试，也不代表
50-run、并发、HITL、MCP 业务效果或完整发布验收；这些范围仍按实际证据分别记账。

## 可信证据

`scripts/run_test_lane.py` 在 `artifacts/test-quality/<lane>/` 生成：

- `junit.xml`：每个 testcase 带精确 `agentgov_nodeid` 属性；
- `coverage.json`：同一 pytest 进程产生的 coverage；
- `evidence.json`：提交 SHA、tracked dirty 状态、策略和依赖哈希、全局/选择集 digest、版本、耗时、worker 配置、逐叶子结果及 artifact 哈希。

校验器交叉解析 JUnit、coverage 和 evidence，拒绝提交不一致、部分选择、额外测试、skipped/xfail/failed 叶子、内容篡改、符号链接和路径逃逸。证据只描述本地执行事实，不依赖远端运行编号或任务名称。

## Shadow 晋级

TIA 和 xdist 初始模式均为 `shadow`，不得直接缩小提交前验证范围或替换串行全量。晋级至少同时满足：

1. 至少 20 组同 SHA 配对样本，且样本跨越至少 14 个日历日；
2. collection 与逐叶子 outcome 完全一致；coverage 的统计宇宙相同、两边独立通过门槛，line/branch 差值绝对值不超过 0.10 个百分点；
3. TIA 零漏测，xdist 零并行特有失败、资源泄漏或顺序污染；
4. xdist p50 至少提速 20%，CPU 分钟增幅不超过 50%；
5. 多个配置合格时选择 p95 最低者；差距不超过 5% 时选择 worker 更少者。

未知路径、依赖、测试策略或共享治理配置变更必须 fail-closed 回退 `main-full`。提交和发版前始终保留完整串行验证，选择性测试不能取代全量回归。

## Mutation 与指标

`make mutation-test` 读取同一策略中的目标、测试选择、时间预算和最低 score，并核对 `pyproject.toml` 的 mutmut 配置，防止两个入口漂移。当前只对高风险集中状态机运行，后续扩展必须先给出风险和成本依据。

持续评审至少关注：目标测试与完整测试的 p50/p95、flaky 与重跑后通过率、隔离数量和平均时长、最慢 10% 耗时占比、失败到定位的时间、owner/capability 缺失率、重复资产组、真实缺陷发现比例、线上逃逸缺陷和高风险变更 mutation score。

## 常用命令

```bash
# 严格 schema、真实 collection、分类与主流程绑定
.venv/bin/python scripts/check_test_quality_policy.py --manifest-only

# 完整离线提交门
make test

# 产品主流程
make main-flow-test

# 一次刷新 + 三路只读 core 容器检查
make container-core-smoke

# 按风险执行 mutation lane
make mutation-test

# AgentScope 单路径静态切换硬门
make cutover-check

# 当前工作树重建后的三服务真实容器验收
make container-core-smoke COMPOSE_ENV_FILE=/path/to/compose.env

# 显式授权的真实 provider 正式链路；仍在一次性 project/root 中执行
REQUIRE_LIVE_RUNTIME=1 \
REAL_ACCEPTANCE_AGENT_ID=security-operations-expert \
REAL_SCENARIO_FILE=/outside/reviewed-scenarios.json \
make container-live-test COMPOSE_ENV_FILE=/path/to/compose.env

# 非正式技术集成诊断；使用独立 Agent 身份，不能升级为业务验收证据
REQUIRE_LIVE_RUNTIME=1 \
TECHNICAL_SCENARIO_FILE=/outside/technical-scenario.json \
make container-technical-live-smoke COMPOSE_ENV_FILE=/path/to/compose.env

# 非正式 Playground 浏览器技术验收；真实 Chromium/API/provider，不验证业务工具效果
REQUIRE_LIVE_RUNTIME=1 \
BROWSER_TECHNICAL_SCENARIO_FILE=/outside/browser-technical-scenarios.json \
make ui-playground-technical-smoke COMPOSE_ENV_FILE=/path/to/compose.env

# 现场部署验收：重建既有项目，使用真实已发布 Agent，保留运行卷与本次验收 Session
REQUIRE_LIVE_RUNTIME=1 \
make ui-playground-deployed-smoke COMPOSE_ENV_FILE=/path/to/compose.env
```

隔离真实容器验收默认从 `docker/.env` 读取 secret，也可显式选择 `COMPOSE_ENV_FILE`；两者都不会
直接作为运行项目配置复用。脚本在互斥锁内创建一次性 env、Compose project、容器前缀、回环端口
和全部宿主挂载。获锁后，runner 以无符号链接的稳定读取将
`REAL_SCENARIO_FILE` / `TECHNICAL_SCENARIO_FILE` 复制到 0700 临时根的 0600 快照；浏览器技术入口
先将 `BROWSER_TECHNICAL_SCENARIO_FILE` 映射为同一受保护的 `REAL_SCENARIO_FILE` 快照。后续所有
release 阶段只接收同一快照路径。快照字节、长度和 SHA-256 同时进入 build 前、recreate 后及
验收后指纹；任一时点发生变化，本轮证据失效。然后基于当前工作树重建镜像并
`--force-recreate` 三个服务，再核对镜像与源码指纹。
验收结束总是清理一次性容器、卷和目录，且只访问 AgentGov API/UI 的公开端口，不触碰既有部署，
不把 AgentScope Runtime 管理面暴露给浏览器，也不自动读取 `docker/.env.local-debug`。

`container-core-smoke` 只证明三服务、readiness、UI 首页和 OpenAPI 的当前工作树容器契约，不调用
真实 provider。`container-live-test` 没有内置场景，必须绑定仓库外人工复核输入和真实已发布
Agent。每条场景必须同时声明 `purpose` 和与之唯一对应的 `capability`；`--runs 50`
是 `generic_runtime` 的精确 50-run 配额，取消、幂等重试和改进效果均单独计数，不得补足通用配额。
`improvement` 场景必须有至少一个非空 `required_test_literals`；真实同输入 baseline 必须缺失至少一项，
candidate 必须全部命中。尚无 action plan / expected-event 验证器的 tool、HITL、team、restart、MCP 和
多轮能力保持 gap；普通非空回复、generic 50-run 或单个 trace 都不能关闭这些 gap。
50 个实质不同 run、10 并发、真实浏览器连续 3 次和 OTLP secret/trace completeness 在
`tests/quality_policy.json` 中保持 `container-live-acceptance` gap，只有对应 evidence 产生后才能关闭。
