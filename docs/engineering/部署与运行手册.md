# AgentGov 部署与运行手册

本文是 AgentGov 当前部署、启动、健康检查、停止和受控恢复的操作入口，面向开发者与平台运维人员。
命令和默认值以仓库当前 `Makefile`、`docker/docker-compose.yml`、env 示例、Runtime settings 与运维脚本
为字段级真相源；本文不另行定义 API schema、业务 Agent Workspace 包契约或产品行为。

相关权威边界如下：

| 主题 | 唯一权威入口 |
| --- | --- |
| HTTP API、认证与 SDK 集成 | [AgentGov 集成指南](../AgentGov集成指南.md) 与运行实例的 `/openapi.json` |
| Workspace 包、导入导出、热加载 | [业务 Agent Workspace 包导入与热加载产品工程方案](../业务AgentWorkspace包导入与热加载产品工程方案.md) |
| Workspace activation `recovery_required` | [业务 Agent Workspace 激活故障恢复 Runbook](./业务AgentWorkspace激活故障恢复Runbook.md) |
| Workspace 自有 pytest 资产 | [业务 Agent Workspace 原生 pytest 测试资产实现方案](./业务AgentWorkspace原生pytest测试资产实现方案.md) |
| vLLM、LiteLLM sidecar 与能力门 | [vLLM 模型网关与 Sidecar 整改优化方案](./vLLM模型网关与Sidecar整改优化方案.md) |
| 测试分层与证据边界 | [测试资产组合治理](./测试资产组合治理.md) |

消失、但 Runtime 中仍留下活动 session turn 的受控恢复。

## 1. 运行模式先选定

AgentGov 的 env 文件按运行环境选择，不是多层覆盖关系。一次进程或 Compose 调用只应消费一份完整
env 文件。

| 消费者 | 完整 env | 默认运行数据根 | 用途与边界 |
| --- | --- | --- | --- |
| Docker Compose / API 容器 | `docker/.env` | `${HOME}/volume-agent-gov` | 日常容器部署和真实容器验收；Compose 注入 `RUNTIME_CONTAINER=1` |
| 宿主机 Python / PyCharm | `docker/.env.local-debug` | `/tmp/local-debug-volume-agent-gov` | 本机调试；不得用其结果声明容器验收通过 |
| Vite 开发服务器 | `frontend/.env.local` | 不持有 Runtime 数据 | 只配置浏览器 API、Langfuse 地址和前端超时 |

不要在正式 env 示例中新增或依赖 `RUNTIME_VOLUME_MODE`。Runtime 由执行环境和容器注入的
`RUNTIME_CONTAINER=1` 选择模式。需要让公共容器验收读取另一份完整 env 时，用调用进程环境选择：

```bash
COMPOSE_ENV_FILE=/absolute/path/to/complete.env make container-core-smoke
```

不要写成 `make COMPOSE_ENV_FILE=...`；公共容器验收会拒绝 Make 命令行变量覆盖和不安全的
`MAKEFLAGS`。

## 2. 前置条件

容器运行至少需要：

- Git；
- Docker Engine 和 `docker compose` v2；
- 能获取或已预装仓库构建所需基础镜像与 Langfuse 镜像；
- 一个本地或内网模型服务。离线模式不等于无模型模式；必需工作流仍需要本地化 LLM；
- 足够的磁盘空间保存镜像、`${HOME}/volume-agent-gov` 运行数据和可选 Langfuse 数据。

执行 `make setup`、宿主机调试或公共验收还需要 `uv`；项目虚拟环境固定使用 Python 3.11。
前端宿主机调试使用 Node.js 22，并按 `frontend/package.json` 的 `packageManager` 使用 pnpm。

开始前确认默认端口未被占用：

| 服务 | 默认宿主机端口 |
| --- | --- |
| AgentGov API | `58080` |
| AgentGov UI | `55173` |
| Langfuse Web（可选） | `53000` |
| Langfuse MinIO API / Console（可选） | `59000` / `59001` |

默认示例面向本地开发，包含仅供开发的默认 token、默认密码和监听 `0.0.0.0` 的服务。任何超出可信开发网段的
部署都必须先用防火墙或反向代理限制入口，并更换所有默认凭据；不要把真实 key 写入仓库、日志、文档
或命令历史。

## 3. 核心服务启动

### 3.1 准备私有 env

在仓库根目录执行：

```bash
make setup
```

该命令只在文件不存在时把 `docker/.env.example` 复制为私有 `docker/.env`，不会覆盖已有私有配置；
同时创建 `.venv` 并安装宿主机工具依赖。随后编辑 `docker/.env`，至少确认：

- `API_KEY` 已替换为私有随机值；
- `MODEL_PROVIDER_BACKEND` 明确为 `anthropic_compatible` 或 `vllm`；
- `MODEL_PROVIDER_API_URL` 指向真实本地或内网模型服务；vLLM 填 base URL，不追加 `/v1`；
- Anthropic-compatible 路径已提供私有 `MODEL_PROVIDER_API_KEY`；vLLM 是否需要 key 由上游服务决定；
- 只启动核心服务时设置 `LANGFUSE_ENABLED=false`；需要采集 Trace 时完成第 6 节配置并使用
  `make all-up`。

不要通过 URL 文本推断模型后端，也不要让本机 API 的治理模型任务复用交互式 Claude `/login`。

### 3.2 构建并启动

```bash
make build
make up
```

`make build` 构建核心服务以及隔离的业务 Agent 测试 sandbox 镜像。`make up` 启动核心 Compose
服务并等待容器健康，包括 LiteLLM sidecar、API、Agent 测试 worker 和 UI。

`make up` 的 Compose 健康门只证明 API `/health/live` 存活，不证明模型路由 ready。启动命令成功后
仍必须执行第 4 节的 readiness 检查。需要观察 API 日志时执行：

```bash
make logs
```

## 4. URL、健康与诊断

默认地址：

| 地址 | 含义 |
| --- | --- |
| `http://localhost:55173` | AgentGov UI |
| `http://localhost:58080/` | API 根入口 |
| `http://localhost:58080/docs` | 自托管 Swagger UI |
| `http://localhost:58080/redoc` | 自托管 ReDoc |
| `http://localhost:58080/openapi.json` | 当前机器可读 OpenAPI 契约 |
| `http://localhost:53000` | 可选 Langfuse UI |

项目关闭了 FastAPI 默认依赖公网 CDN 的文档页面，并在相同路径提供仓内静态资产驱动的
Swagger UI 与 ReDoc。它们适合人工浏览，不是健康门；机器集成继续读取 `/openapi.json`。
`/health` 中的 `swagger` / `redoc` 字段来自 FastAPI 默认配置，当前可能为 `null`，不能据此
断言自托管 `/docs` / `/redoc` 不存在。

按由浅到深的顺序检查：

```bash
curl --fail --silent --show-error http://localhost:58080/health/live
curl --fail --silent --show-error http://localhost:58080/health/ready
curl --fail --silent --show-error http://localhost:58080/health
curl --fail --silent --show-error http://localhost:58080/openapi.json >/dev/null
```

| 检查 | 成功含义 | 失败解读 |
| --- | --- | --- |
| `/health/live` | API 进程可响应；Compose 以此判定 API 健康 | 容器、进程或基础启动失败 |
| `/health/ready` | 缓存的模型 provider readiness 为 ready | 返回 `503` 时进程可能正常，但模型路由不可用 |
| `/health` | 当前控制面、provider 路由与配置状态摘要可读 | 用于定位配置，不替代 readiness |
| `/openapi.json` | 当前实例公开契约可读取 | 不等价于业务主流程可用 |

要让公共入口主动完成核心 readiness 验收，运行：

```bash
make smoke
```

容器启动或 readiness 失败时，先保留输出，再运行：

```bash
make compose-diagnose
docker compose --env-file docker/.env -f docker/docker-compose.yml ps
make logs
```

诊断时重点核对日志中的运行模式、实际选择的 env、数据路径和 provider 路由；不要复制包含私有
endpoint、header、prompt、tool I/O 或 key 的日志到公开渠道。

## 5. env、运行卷与数据边界

容器默认持久化根为 `${HOME}/volume-agent-gov`，不在源码仓库内：

| 宿主机目录 | 容器路径或职责 |
| --- | --- |
| `${HOME}/volume-agent-gov/data` | `/data`；包含 `runtime.sqlite3`、业务 Agent Workspace、per-Agent Git 与运行投影 |
| `${HOME}/volume-agent-gov/governor-workspace` | `/governor-workspace`；Governor live Workspace |
| `${HOME}/volume-agent-gov/claude-roots/governor` | `/claude-roots/governor`；Governor Claude profile |
| `${HOME}/volume-agent-gov/langfuse/*` | 可选 Langfuse 的 PostgreSQL、ClickHouse、Redis 与 MinIO 持久数据 |

`docker/volume/` 只可能作为旧数据迁移来源，不能重新作为正式运行根。宿主机调试默认使用独立的
`/tmp/local-debug-volume-agent-gov`，避免把 PyCharm/uvicorn 与容器同时指向同一 SQLite、Workspace
或 Claude profile。

运维约束：

- 服务运行时不要手工改 `runtime.sqlite3`、Workspace Git、activation journal 或 Claude profile；
- 变更 `HOST_RUNTIME_VOLUME_ROOT` 前先停服，完成仓库外备份，按字节迁移并校验 owner/权限，再修改
  一份完整 env 后执行 `make runtime-validate` 与健康验收；
- live Workspace 可以包含业务所需的私有 endpoint 和凭据，但它是敏感运行资产；回流仓库初始化源前
  先在仓库外形成候选，再通过 `make runtime-bootstrap-scan` 准入；
- `make runtime-clean`、`make local-debug-clean` 和 `make clean-runtime-artifacts` 不是日常停止命令，
  只有明确理解其精确清理范围并已有备份时才使用；
- 不用手工 `chown -R` 或放宽整棵运行根权限来处理单点权限问题。

当前运行卷的初始化和契约检查使用：

```bash
make runtime-bootstrap
make runtime-validate
```

业务 Agent Workspace 的复杂导入、覆盖、恢复与 activation journal 处理不在本文展开，按开头链接的
工程方案和恢复 Runbook 操作。

## 6. Langfuse 自托管观测

Langfuse 是可选的本地开发观测面。启用前在私有 `docker/.env` 中：

- 替换 NextAuth、salt、encryption、PostgreSQL、ClickHouse、Redis、MinIO 和初始化项目的全部默认
  secret/credential；
- 确认 `LANGFUSE_NEXTAUTH_URL` 与浏览器实际访问地址一致；
- 仅本机访问时设置 `LANGFUSE_BIND_IP=127.0.0.1`；需要远端访问时通过可信网络、防火墙或反向代理
  限制入口；
- 需要 Runtime 写 Trace 时启用 `LANGFUSE_ENABLED=true` 并配置对应 public/secret key；不需要采集时
  保持关闭。

首次或全量启动核心服务与 Langfuse：

```bash
make all-up
```

若核心服务已经运行，只启动 Langfuse 六个 profile 服务：

```bash
make langfuse-up
```

`make all-up` 和 `make langfuse-up` 都会先执行受限的一次性 volume initializer。不要用宿主机递归
改权命令代替它。启动后检查：

```bash
make langfuse-smoke
make langfuse-logs
```

只停止 Langfuse、保留核心服务：

```bash
make langfuse-stop
```

开发观测会按私有 env 中的开关保留 prompt、tool、治理任务和 Trace I/O；这些内容可能含业务敏感信息。
Langfuse UI、MinIO Console 和其持久卷必须按敏感运行资产保护，不能因其是调试面而对不可信网络开放。

## 7. 公共容器验收

真实容器结论只能来自下列公共 Make 入口。它们以当前工作树（包括相关未提交内容）形成受管候选，
重新构建镜像并以 `--force-recreate` 刷新所需 Compose 服务，再保存本轮验收回执；不应以私有脚本、
已有容器或宿主机测试结果替代。

| 入口 | 证明范围 |
| --- | --- |
| `make smoke` | provider readiness、配置与健康诊断；不执行 Agent turn |
| `make container-core-smoke` | 同一刷新下的 readiness、UI 首页和 OpenAPI 只读检查 |
| `make container-openapi-check` | 当前 OpenAPI 契约与容器投影 |
| `make ui-smoke` | UI 容器与浏览器基础路径 |
| `make ui-feedback-smoke` | 改进治理工作台真实浏览器路径 |
| `make ui-openai-responses-smoke` | OpenAI Responses 兼容交互路径 |
| `make ui-playground-cancel-smoke` | Playground 取消路径 |
| `make container-live-test` | 真实 Compose、真实模型和 Runtime 主路径 |
| `make container-workspace-pytest-test` | 指定业务 Agent 精确 commit 的隔离 Workspace pytest |
| `make container-speech-summary-test` | Speech Summary 与 raw event 路径；会产生敏感验收证据 |
| `make container-health-e2e` | 隔离 provider health、超时和恢复路径 |
| `make langfuse-smoke` | Langfuse profile 与 Trace 接入 |

日常核心部署至少执行：

```bash
make container-core-smoke
```

发布、完整验证或主流程变更还要按风险运行 `make test`、`make main-flow-test` 和对应 live/UI/Langfuse
入口。`make test` 是宿主机质量门，不能单独证明容器部署通过；local-debug 结果也不能替代任何公共
容器回执。

## 8. 可信主机部署

只向已纳入组织信任管理、由操作者拥有权限的 Docker Compose 主机部署。部署脚本固定以下安全边界：

- 只部署显式的本地完整 40 位 Git commit，不包含未提交工作树；
- `known_hosts` 必须预先包含目标主机，禁止首次连接自动接受 host key；
- 目标用户、主机、绝对目录和 Compose project 必须显式给出，`--confirm-target` 必须逐字重复目标；
- 只替换命名的 Compose project，并保留远端私有 `docker/.env`；
- 本地构建项目镜像，传输并在远端以 `--no-build --pull never` 启动核心服务和完整 Langfuse profile；
- 成功后检查 API、UI、Langfuse，并在远端项目目录写入私有部署回执。

本机需要 Git、Docker、gzip、realpath、rsync、SSH、ssh-keygen 和 tar；远端需要 Python 3、Docker 与
`docker compose`。部署前先确认源 commit 已完成所需质量门和公共容器验收，再执行：

```bash
scripts/deploy_agent_gov_to_host \
  --target <trusted-host> \
  --user <deploy-user> \
  --remote-dir <absolute-project-path> \
  --known-hosts-file <absolute-canonical-known-hosts-file> \
  --source-commit <full-40-character-commit> \
  --project-name <compose-project> \
  --change-id <auditable-change-id> \
  --confirm-target <deploy-user>@<trusted-host>:<absolute-project-path>
```

首次部署会在空且未标记的远端目录建立目标标记，并从提交中的示例创建私有 `docker/.env`；示例凭据
不能作为可暴露部署。首次引导前必须先在主机网络/防火墙层禁止不可信访问；脚本建立受管目录后，
通过可信通道填写远端私有 env、替换全部默认凭据，再以新的可审计 `change-id` 重新部署和验收。
后续部署保留该私有 env，不会用仓库示例覆盖。

脚本的 HTTP 检查证明 API/UI/Langfuse 入口可响应，不替代模型 readiness、业务主流程或数据迁移验收。
部署完成后仍应从目标主机执行 `/health/ready`，并按变更风险执行外部用户路径验收。不要把远端私有
env、部署回执、镜像归档、运行卷或日志同步回源码仓库。

## 9. 停止、重启与回退

停止核心 Compose project：

```bash
make down
```

该入口没有传入 `-v`，不会把 `${HOME}/volume-agent-gov` 的 bind-mounted 运行数据当作停止步骤删除。
不要用 `docker compose down -v`、删除运行根或 `make runtime-clean` 代替正常停止。

配置变更后的标准重启：

```bash
make down
make build
make up
make container-core-smoke
```

回退可信主机应用版本时，使用第 8 节脚本重新部署一个已经验收过的旧完整 commit，并使用新的
`change-id` 留下独立审计记录。不要在远端目录直接 `git checkout`，也不要复用旧部署回执冒充本次
验证。

应用代码回退不会自动回退 SQLite、Workspace Git、Langfuse 数据或其他持久卷。执行前必须：

1. 停止写入并记录当前部署 commit、VERSION、目标 commit 和数据迁移版本；
2. 在仓库外备份 `${HOME}/volume-agent-gov`，验证备份可读且范围正确；
3. 确认目标代码对现有数据库 schema 和 Workspace 数据向后兼容；不兼容时先制定独立数据恢复方案；
4. 部署旧 commit 后重新执行 readiness、核心容器和受影响业务主流程验收。

业务 Agent 自身的版本恢复属于 Workspace/版本治理 API，不等于平台宿主机代码回退，按集成指南与
Workspace 工程方案处理。

## 10. 孤立 session turn 恢复

### 10.1 何时允许使用

只有在 Workspace 导入、恢复、删除或其他需要 session invalidation 的动作返回
`WORKSPACE_SESSION_INVALIDATION_CONFLICT`，且日志与进程证据确认原 Runtime turn 已经孤立时，才使用
本节工具。lease 过期本身不是“执行已经停止”的证明。

执行前必须：

- 暂停目标 Agent 的新对话、Workspace 变更、测试和发布；
- 核对 API/SDK 日志、容器/进程、活动工具调用和 HITL 请求，确认没有原执行仍在推进；
- 记录准确 `agent_id` 与候选 `run_id`；
- 停止写入或使用 SQLite 一致性 backup 机制备份运行数据库，不能直接复制仍带活动 WAL 的文件；
  同时保证恢复期间没有另一个操作者处理同一 turn。

如果故障是 Workspace activation operation 自身留下 `recovery_required` 围栏，不使用本工具，转到
[业务 Agent Workspace 激活故障恢复 Runbook](./业务AgentWorkspace激活故障恢复Runbook.md)。

### 10.2 只读 dry-run

工具默认只读，从当前 Runtime settings 选择数据库，不接受任意数据库路径。先扫描目标 Agent：

```bash
docker compose --env-file docker/.env -f docker/docker-compose.yml \
  run --rm --no-deps claude-agent-api \
  run-tool python -m app.runtime.session_turn_recovery \
  --agent-id <agent-id>
```

已知候选时，用可重复的 `--run-id` 缩小检查范围：

```bash
docker compose --env-file docker/.env -f docker/docker-compose.yml \
  run --rm --no-deps claude-agent-api \
  run-tool python -m app.runtime.session_turn_recovery \
  --agent-id <agent-id> \
  --run-id <runtime-run-id>
```

保存同一次 dry-run 输出中的 `operation_id`、`state_digest`、候选列表和 blockers。只有目标候选
`eligible=true` 且证据与实际事故一致时才能继续。已有 committed entry、既有 AgentRun、未解决 HITL、
session/owner 不匹配或状态已变化都会阻断恢复。

### 10.3 精确 apply

复制同一次 dry-run 的围栏值并明确列出每个目标：

```bash
docker compose --env-file docker/.env -f docker/docker-compose.yml \
  run --rm --no-deps claude-agent-api \
  run-tool python -m app.runtime.session_turn_recovery \
  --agent-id <agent-id> \
  --run-id <runtime-run-id> \
  --operation-id <dry-run-operation-id> \
  --state-digest <dry-run-state-digest> \
  --reason "confirmed orphan after original runtime process stopped" \
  --apply
```

多个 `--run-id` 在一个事务中全成或全败。状态摘要变化时不要重用旧值，重新 dry-run；完全相同的
operation 重试是幂等的，不同 operation 不能再次应用到已经恢复的 turn。

`--force-unexpired` 只允许在 apply 时使用，且仅当独立证据确认原执行已经停止、但 lease 尚未过期时
追加。它不是跳过 blocker 或强制中断活跃任务的通用选项。

成功 apply 会把目标 running turn 标记为 interrupted，丢弃未提交的 SDK staging entry，原子创建并
完成 AgentRun 投影并清除 session fence；它不会增加 session `turns`，不会擦除已提交历史或 SDK
session 映射。完成后使用同一 `agent_id` 和 `run_id` 再做一次只读扫描，确认候选不再处于活动状态，
再恢复上游操作。

不要通过 SQLite 写命令、删除 session 行、篡改 lease 或手工清理 SDK transcript 绕过该事务围栏。

## 11. 宿主机 / PyCharm 本机调试

### 11.1 准备独立环境

```bash
make setup
make local-debug-env
```

编辑私有 `docker/.env.local-debug`，配置宿主机可访问的模型 provider、API key 和 MCP 地址。该文件由
宿主机 Python 自动选择，Docker Compose 不读取它；不要同时把它当作 `docker/.env` 的覆盖层。

准备并检查独立运行根：

```bash
make local-debug-bootstrap
make local-debug-validate
```

命令默认只操作 `/tmp/local-debug-volume-agent-gov`。不要为了复用已有数据而把它改成容器运行根；
SQLite、Workspace 和 Claude profile 被两个进程同时持有会破坏调试结论并增加数据风险。

### 11.2 启动 API

命令行启动：

```bash
.venv/bin/python -m app.runtime.service_launcher api
```

PyCharm Run/Debug 配置：

| 字段 | 值 |
| --- | --- |
| Module name | `app.runtime.service_launcher` |
| Parameters | `api` |
| Working directory | 仓库根目录 |
| Python interpreter | `<repo>/.venv/bin/python` |
| Environment variables | 留空，让 Runtime 自动选择 `docker/.env.local-debug` |

宿主机 API 默认为 `http://localhost:8080`。按第 4 节把端口换成 `8080` 检查 liveness、readiness、
health 和 OpenAPI。

### 11.3 启动前端

```bash
cp -n frontend/.env.example frontend/.env.local
```

把 `frontend/.env.local` 中以下地址改为宿主机 API：

```dotenv
VITE_RUNTIME_API_BASE=http://localhost:8080
VITE_RUNTIME_API_KEY=<local-debug-api-key>
VITE_DEV_PROXY_TARGET=http://localhost:8080
VITE_LANGFUSE_URL=http://localhost:53000
```

然后启动：

```bash
corepack pnpm --dir frontend install --frozen-lockfile
corepack pnpm --dir frontend dev
```

其中 `VITE_RUNTIME_API_KEY` 只填写与 `docker/.env.local-debug` 一致的本地调试 token，不得填写模型
provider key。UI 默认为 `http://localhost:5173`。Vite dev server 监听 `0.0.0.0`，只在可信开发网络
使用；需要跨主机访问时同时评估浏览器可见的 `VITE_*` 配置，任何上游真实 secret 都不得放入前端 env。

本机调试完成后停止 Python/Vite 进程。只有确认不再需要本机运行产物时才执行：

```bash
make local-debug-clean
```

该清理命令不等于删除容器运行卷；执行前仍应检查输出目标。最终部署结论必须回到第 7 节公共容器
入口验证。

## 12. 运行变更的同步条件

以下事实变化时必须同步修订本文，并运行 docs 治理检查：

- Make 公共启动、停止、诊断或容器验收入口变化；
- Compose 服务、profile、端口、healthcheck、挂载或持久化根变化；
- `docker/.env`、`docker/.env.local-debug`、`frontend/.env.local` 的选择规则变化；
- Langfuse 初始化、安全边界或 Trace 采集默认值变化；
- 可信主机部署参数、目标身份校验、部署回执或回退策略变化；
- session turn 恢复 CLI、围栏字段或事务语义变化。

字段级契约仍应修改其代码、OpenAPI、env 示例或专用 Runbook；本文只同步操作者需要执行的稳定入口，
不复制内部实现清单。
