## 1. 当前主链路

```text
反馈来源
  -> ImprovementItem
  -> NormalizedFeedback
  -> Attribution
  -> OptimizationPlan
  -> ExecutionRecord / AgentChangeSet
  -> RegressionTestDesign
  -> Workspace tests/test_*.py
  -> AgentTestRun
  -> Release / rollback
```

当前用户主链路只有四个阶段：反馈整理、归因分析、优化执行、测试发布。后端内部状态、Git 操作、
治理 Agent 调用和平台测试运行只服务这四个阶段，不形成平行产品流程。

## 2. 核心对象与所有权

| 对象 | 所有者 | 当前作用 |
| --- | --- | --- |
| `ImprovementItem` | 后端 | 聚合反馈并承载阶段、归属和内容引用。 |
| `NormalizedFeedback` | 用户 + 治理 Agent | 反馈整理阶段的结构化事实。 |
| `Attribution` | 治理 Agent，用户确认 | 归因结论、证据、置信度和待确认项。 |
| `OptimizationPlan` | 治理 Agent，用户确认 | 优化动作、风险、验证建议和执行目标。 |
| `ExecutionRecord` | 后端 | 隔离 worktree 中实际应用的变更、Diff、待发布提交和回滚信息。 |
| `AgentChangeSet` | 后端 | 同一未发布改动的业务容器；可以在返工后指向更新的待发布提交。 |
| 回归测试代码候选 | 治理 Agent + 平台，用户确认 | 治理 Agent 输出完整 pytest 代码、测试意图和断言依据；平台确定路径。确认前是待审查 Diff，不是长期测试资产。 |
| `tests/test_*.py` | 业务 Agent Workspace | 可执行测试资产的唯一真相源，与 Agent 代码和配置一起进入 Git。 |
| `AgentTestRun` | 平台 | 固定 pytest 命令在精确提交上的持久化执行证据。 |
| `AgentTestSchedule` / `AgentTestScheduleEvent` | 平台 | 每 Agent 唯一定时策略及每个计划窗口的触发审计；不保存测试正文。 |
| `Release` | 后端 | 发布、强制发布警告、恢复和回滚记录。 |
| `AssetRecord` | 后端 | 方法论、执行和审计等通用 Registry 资产；不复制 Workspace 测试内容。 |

所有注册业务 Agent（含 `main-agent`）遵循相同的 Workspace、测试、变更集和发布机制。`governor`
是治理执行者，不进入业务 Agent 注册表、Playground 业务选择器或业务发布链。

## 3. 四阶段内容契约

- 反馈整理：归并来源并确认 `NormalizedFeedback`。
- 归因分析：治理 Agent 生成 `Attribution`，用户确认或返回整理阶段修正事实。
- 优化执行：生成并确认 `OptimizationPlan`；后端在隔离 worktree 应用确定性动作并产生
  `ExecutionRecord`、Diff、`AgentChangeSet` 和待发布提交。
- 测试发布：治理 Agent 生成回归测试代码候选；后端校验并确定 `tests/test_feedback_*.py` 路径。
  用户确认待发布变更后，后端只新增测试文件，并把配置和测试收口为相对修复前版本的同一待发布
  commit；用户再显式运行完整 `tests/`，平台才创建待发布检查 `AgentTestRun`。该确认动作不调用定时策略。

内容生成、确认、执行和测试物化会校验同一事项、业务 Agent、执行记录和变更集的依赖关系。
客户端不能提交后端拥有的 job ID、提交 SHA、状态、运行结果或 provenance 来伪造阶段完成。

### 3.1 产物存在性与前端读取

`GET /api/improvements` 和 `GET /api/improvements/{improvement_id}` 的每个事项都必须包含
`artifact_presence`。其中五个布尔字段分别表示 `NormalizedFeedback`、`Attribution`、
`OptimizationPlan`、`ExecutionRecord` 和 `RegressionTestDesign` 的持久化行当前是否存在。
该投影由后端在事项查询中直接检查内容表，不由 `improvement_stage` 推导，也不新增第二份持久化状态。

前端先读取事项，再只对值为 `true` 的产物发起对应 GET；`false` 是正常空态，不应通过一次必然
404 的请求来探测。值为 `true` 后子资源仍返回 404，表示列表投影与随后读取之间发生并发变化，
页面必须显示可重试错误，不能静默伪装为空。阶段只决定用户当前看到的工作面板和下一业务动作，
不能替代产物存在性；这是为了覆盖早期阶段已产生 no-action 执行/回归记录、返工删除下游产物以及
历史稀疏数据等合法组合。

GET 读取仅对网络错误、超时和 `408/429/502/503/504` 重试一次；调用方主动取消、JSON 解码失败、
其他 4xx、`500` 和所有写请求均不自动重试。验收同时要求：稀疏投影只用一个事项列表 SELECT、
OpenAPI 将五个字段声明为必填布尔值、前端单测覆盖请求矩阵，并且 mock 浏览器主流程中不存在
非预期 console error、request failure 或 HTTP error。若未来改为原子返回事项与全部内容的复合
详情契约，可重审请求编排，但不得重新以阶段猜测持久化事实。

该投影直接从现有内容表派生，不需要 SQLite migration。滚动升级必须先发布后端、再发布前端：
旧前端会忽略新增响应字段，新前端在旧后端缺少该字段时会按契约错误 fail-closed。

## 4. Workspace pytest 测试资产

每个业务 Agent 的测试随 Workspace 管理：

```text
workspace/tests/
├── README.md
├── conftest.py       # 可选
└── test_*.py
```

首版只接受 `tests/` 下的扁平 Python 测试文件。导入包缺少 `tests/`、说明文件或测试文件时允许导入，
但返回结构化 warning；没有可运行测试的版本不能满足普通发布条件。新建和覆盖导入都要求包根目录
`agent.yaml.agent.id` 有效，并与 API URL 中的目标 `agent_id` 逐字一致；缺失、无效、格式错误
或来源 ID 不一致会在任何 Workspace、注册表、Git 或会话变更前被明确拒绝。

`RegressionTestDesign` 只表达候选测试语义。用户确认后，后端才把它确定性物化为不可覆盖、不可删除、
不可弱化的测试文件。测试文件、fixture 和辅助资产随 Workspace Git 提交，平台不再维护数据库测试集、
全局用例池或第二份测试正文。

完整工程契约见
[业务 Agent Workspace 原生 pytest 测试资产实现方案](./engineering/业务AgentWorkspace原生pytest测试资产实现方案.md)。

## 5. 平台测试运行（Phase 7 工作树已验证，尚未发布）

手工、待发布变更和定时入口最终都绑定一个不可移动的完整 Git commit；客户端不能选择测试命令、
工作目录、状态或权威报告。平台把请求写成持久化 `AgentTestRun`，由独立 worker 在固定、无网络、
受限资源的 sandbox 中执行 Workspace 自带测试，并保存可审计的终态回执。

这条 lane 证明“精确提交在固定隔离环境中执行过”，不独立证明业务正确性、能力质量或真实 Agent
行为。发布资格仍由后端依据提交身份、测试结果、运行来源和清理证据判定；pytest 产生的业务报告
只作有界诊断。进程重启、遗留运行和临时会话必须显式收口，不能伪装为成功或可恢复状态。

资产复利中心按业务 Agent 展示当前有效 commit 的测试文件、suite 诊断、运行历史和定时策略；测试
源码始终从 Workspace Git 只读投影，不写入通用资产表。定时策略只负责触发测试，不读取候选
worktree，也不推进发布状态。

固定命令、挂载、worker authority、回执字段和公共容器验收入口只在
[业务 Agent Workspace 原生 pytest 测试资产实现方案](./engineering/业务AgentWorkspace原生pytest测试资产实现方案.md)
维护；跨 lane 的选择与验收规则见
[测试资产组合治理](./engineering/测试资产组合治理.md)。当前候选是否已经通过终验，以
[`.planning/STATE.md`](../.planning/STATE.md) 和
[Phase 7 验收报告](../.planning/phases/07-per-agent-lane/07-VERIFICATION.md) 为准。

## 6. 版本与发布条件

Git `commit_sha` 是被测版本的唯一权威标识；`suite_digest` 是从该提交测试文件派生的完整性摘要，
`change_set_id` 只用于关联同一未发布改动。不得把三者拼成新的人工版本身份。
手工 `POST /api/agent-test-runs` 必须显式传入资产视图或仓库 API 返回的完整 40 位 `commit_sha`；
后端不会替调用方解析移动的“当前版本”。独立 worker 只物化该提交，在上述无网络 sandbox 中运行
固定隔离命令，终态 typed receipt 固化 source/tree/suite、镜像、隔离、结果和清理证据。
这条 static lane 验证 Workspace 代码契约，不替代 P1 的真实 Agent 行为测评。

普通发布至少要求：

- 归因、执行和待发布版本 provenance 完整；
- 当前 `AgentChangeSet.candidate_commit_sha` 存在；
- 同一业务 Agent、同一待发布 `commit_sha` 存在 `passed` 且 typed receipt、source/suite digest、
  cleanup 均经后端校验的平台测试运行；
- 当前没有其他发布阻塞项。

上述 Workspace 运行是工程卫生必要门，不是能力或安全独立通过的充分条件。P1 发布测评落地后，最终
发布决定还必须组合 evaluator-owned assessment、同协议 comparison 与 safety gate。

旧提交上的通过记录不能放行更新后的待发布提交。失败、错误、取消、中断、空测试目录或只有测试设计
也不能放行。UI 使用“修复前版本”和“待发布版本”，不把“基线/候选”作为用户标签。

反馈闭环待发布版本必须在当前精确提交上运行完整 `workspace/tests/`，已有失败和新增失败都必须整改；
反馈发布工作台不提供 force 入口。受保护 API 的 `force=true` 也只表示全部门禁已满足后的管理员加急
与审批审计，不能绕过测试、provenance 或其他阻塞项。历史 release 的 `force_publication_blocker`
非空时，UI 明确标注为升级前“可绕过阻断项”的旧策略记录，并继续展示原阻塞项、原因和操作人；
它不恢复旧能力，也不能放行新的发布。

## 7. 公开 API 的发现方式

运行时 `/openapi.json` 是路由、字段、状态码、弃用标记和请求体的唯一机器可读真相源；本文不复制
完整路径清单。当前公开面按四阶段内容、测试资产、平台测试运行、测试定时策略和版本治理组织。
集成顺序与稳定入口见 [AgentGov 集成指南](./AgentGov集成指南.md)，调试 UI 见自托管 `/docs` 与
`/redoc`。任何文档示例与 OpenAPI 冲突时，以同一运行版本导出的 OpenAPI 为准。

## 8. 存储与迁移

- `${HOME}/volume-agent-gov/data/runtime.sqlite3` 保存事项内容、变更集、平台测试运行、发布和审计记录。
- `${HOME}/volume-agent-gov/data/business-agents/<agent_id>/workspace` 保存业务 Agent Git Workspace；
  worktree 与发布归档位于同一 Agent 的 `version/` 下。
- SQLite migration `0048` 至 `0054` 完成旧测试模型归档、pytest 资产、调度和执行证据迁移；
  migration `0055` 增加 Workspace 激活日志与 Git authority 约束；migration `0056` 增加 durable
  Agent 删除 journal；migration `0057` 增加 operator recovery attempt；migration `0058` 幂等重装
  前述 authority triggers；migration `0059` 补齐删除 journal 的转移与终态约束。这里仅保留迁移
  范围，精确 SQL 与触发器以迁移代码为准，操作安全契约见 Workspace 工程方案和故障恢复 Runbook。
- 历史迁移、归档文档和负向测试可保留旧名称，但它们不是兼容入口，也不得重新进入主流程。

## 9. 明确不再成立的设计

- 数据库测试集、全局测试用例池和逐用例人工复核不是当前测试资产模型。
- 测试内容不写入通用 `AssetRecord.body`；资产复利中心只从 Workspace Git 只读投影源码，并从运行库
  投影运行与调度证据。
- 平台不接收上传后的任意 pytest 命令，不自动安装测试依赖，也不把本地断言回传解释成权威结果。
- `main-agent` 没有特殊测试或发布通道。
- 治理 Agent 不作为业务 Agent 被导入、选择、测试或发布。
