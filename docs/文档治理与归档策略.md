# 文档治理与归档策略

本文档是 `docs/` 目录治理的入口说明和权威地图，用于说明文档治理时应先看哪里、由谁承载规则、如何验证结果。具体执行流程由 `docs-governance` skill 承载，活跃文档和归档文档分别由 README 索引维护。

## 治理目标

- 让活跃文档、历史文档、评审证据和工程流程各有入口。
- 消除同一主题的重复权威，避免旧设计继续影响当前整改。
- 保留有审计和迁移价值的历史文档，但移出活跃阅读路径。
- 把可复用的文档治理流程放入 skill，把可机械判定的规则放入脚本。

## 权威地图

| 治理对象 | 权威来源 | 说明 |
| --- | --- | --- |
| 活跃阅读路径 | `docs/README.md` | 新增活跃 Markdown 文档必须能从这里发现。 |
| 归档清单 | `docs/archive/README.md` | 记录原路径、归档路径、替代文档和归档日期。 |
| 术语和版本层级 | `docs/AgentGov术语与版本边界.md` | 区分长期产品术语、当前实现事实和四阶段改进治理方案。 |
| 产品成熟度与阶段状态 | `.planning/STATE.md` | 区分已验证、已实现待终验和规划中；文档不得自行升级状态，也不得把工作树验收写成已发布。 |
| 发布版本 | 根 `VERSION`、对应 Git tag 与发布回执 | 三者一致后才能声明能力已经发布；阶段完成本身不等于发布。 |
| 当前实现事实 | `docs/反馈闭环当前实现基线.md`、运行时 OpenAPI 与当前代码 | 基线解释对象和链路；字段与路由以 OpenAPI/代码为准。 |
| 改进治理工作台 UI | `docs/AgentGov_四阶段改进治理工作台UI整改方案.md` | 只负责四阶段用户主链路、信息归属、交互语义和设计验收，不承载测试执行协议。 |
| 测试资产与执行契约 | `docs/engineering/测试资产组合治理.md`、`docs/engineering/业务AgentWorkspace原生pytest测试资产实现方案.md` | 前者负责分权与质量策略，后者负责 Workspace pytest 的当前工程协议。 |
| 部署与运行 | `docs/engineering/部署与运行手册.md` | Compose、env、健康诊断、Langfuse、主机部署和本机调试的唯一操作入口。 |
| 文档治理动作流程 | `.codex/skills/docs-governance/SKILL.md` 与 `.claude/skills/docs-governance/SKILL.md` | 判断保留、合并、拆分、归档、删除或移入 skill。 |
| 文档边界矩阵 | `.codex/skills/docs-governance/references/docs-boundary.md` 与 `.claude/skills/docs-governance/references/docs-boundary.md` | 记录可复用判断标准和反例。 |
| 机械治理规则 | `scripts/check_docs_governance.py` | 检查 docs 入口、归档索引、skill 镜像和未完成标记。 |

## 使用原则

- 新增、移动、重命名、拆分、归档或删除 `docs/` 文档时，先使用 `docs-governance` skill。
- 文档必须提供足以让目标读者理解意图、边界和判断依据的最小充分论证；不是只列结论，也不堆叠调查流水账。
- 根 `README.md` 是产品入口，不是 API、迁移、sandbox、回执字段或故障恢复协议的镜像；
  README 只保留价值、成熟度、五分钟启动、稳定边界和任务导航。
- 能力成熟度统一为“已验证”“已实现待终验”“规划中”“已废弃”；交付边界另行标明“当前发布”
  或“当前工作树”。“代码存在”“宿主测试通过”或“方案已冻结”都不能自动升级为“已验证”，
  “阶段已验证”也不能自动升级为“已发布”。
- 新增或修改权威原则、公开契约和不可逆工程决策时，至少说明实际问题、事实依据、主要替代方案未采用原因，以及修订或退出条件。
- 涉及 AgentGov 产品定位、目标愿景使命、反馈闭环、多业务 Agent 或资产沉淀时，先使用 `agentgov-governance-preflight` 做内容建模，再决定文档容器动作。
- 与四阶段改进治理工作台 UI 整改方案冲突的旧 UI 设计、ASCII 草图、旧五类 Agent 工作台设计和旧验收口径，均不再作为未来主流程依据。
- 当前实现基线文档可以保留真实 API、数据库、测试和 UI 名称，但必须区分已发布基线、
  已验证但未发布的工作树、待验实现和目标态；不能用目标方案覆盖当前缺口，也不能把工作树能力
  写成已发布能力。
- 旧文档不因“旧”而自动归档或删除；只有替代关系、引用迁移、审计价值和活跃阅读路径都清楚后才行动。
- 目录细则、归档明细和术语正文不放在本文档中，分别由 README、archive 索引和术语文档维护。

## 最小充分论证

论证深度随文档角色变化：

| 文档角色 | 最少需要回答 |
| --- | --- |
| 权威原则 / 宪法 | 为什么是稳定原则、事实基础是什么、替代方案为何不选、何时修订 |
| 产品或工程契约 | 用户问题、对象与边界、关键裁决、失败语义、验收方式 |
| 当前实现基线 | 当前代码或运行态证据、已知限制、与目标态的边界 |
| runbook / 操作说明 | 前置条件、命令或动作、成功证据、失败处理 |
| 评审 / 复盘 | 发现、证据、影响、整改或不整改理由 |

以下内容不属于有效论证：

- 只有“应该、必须、最佳实践”而没有适用问题和事实边界；
- 只罗列命令、聊天过程或调查时间线；
- 为显得完整而预埋当前阶段不需要的状态机、安全模型或兼容层；
- 用文档目标态替代尚不存在的代码、机器策略或运行态证据。

## 动作口径

文档治理输出统一使用以下动作，便于审查和复用：

| 动作 | 含义 |
| --- | --- |
| `keep` | 保留为活跃入口或当前实现基线。 |
| `merge` | 合并到现有权威文档，避免并列维护。 |
| `split` | 按读者、权威性或流程边界拆分。 |
| `move-to-skill` | 将可复用操作流程或判断标准移入 skill 或 reference。 |
| `archive` | 移入 `docs/archive/`，保留审计和迁移价值。 |
| `delete` | 删除没有长期读者、唯一信息或审计价值的临时材料。 |
| `no-op` | 保持现状，并说明本轮不改的原因。 |

## 验证

文档或 skill 变更后至少运行：

```bash
git diff --check
.venv/bin/python scripts/check_docs_governance.py
.venv/bin/python scripts/check_stage_language.py
.venv/bin/python scripts/check_codex_governance.py --mode fail
```

移动、归档或删除文档前，先检查旧路径引用：

```bash
rg -n "旧文件名|旧相对路径" README.md docs .planning AGENTS.md .codex .claude
```

验收标准：

- 活跃文档能从 `docs/README.md` 发现。
- 归档文档能从 `docs/archive/README.md` 追溯。
- 旧设计不会与四阶段 UI 整改方案并列成为未来依据。
- skill、docs 和脚本各司其职，不重复维护同一套长篇规则。
- 权威原则和公开契约具备最小充分论证，读者能判断其意图、适用边界和退出条件。
