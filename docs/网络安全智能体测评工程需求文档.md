# 网络安全智能体测评工程需求文档

> 文档角色：产品能力目标方案，不代表当前 OpenAPI、数据库、前端或运行态已经实现。
> 版本：V1.0
> 状态：讨论稿
> 适用范围：网络安全运营、威胁分析、告警研判、事件调查、响应处置、安全数据标准化等业务 Agent 场景。
> 核心原则：以标准定义任务、以场景产生数据、以事实图保存答案、以工具轨迹观察过程、以安全边界约束行动、以回归测试推动持续改进。

## 0. 文档定位与 AgentGov 边界

### 0.1 权威关系

本文定义网络安全垂域的测评能力目标、场景模型、评分原则、MVP 范围和验收条件。它是
AgentGov 通用治理平台上的领域能力方案，不改变 AgentGov 的长期产品定位，也不把安全运营
收窄为平台唯一场景。

相关权威关系如下：

- AgentGov 的长期定位、治理对象和三层资产模型以
  [智能体治理平台 AgentGov 目标、愿景与使命](./项目目标愿景使命.md) 为准。
- 业务 Agent、治理 Agent、改进事项、四阶段改进治理和资产 Registry 的术语以
  [AgentGov 术语与版本边界](./AgentGov术语与版本边界.md) 为准。
- 当前反馈、归因、优化、测试和发布链路以
  [反馈闭环当前实现基线](./反馈闭环当前实现基线.md) 为准。
- 当前可执行回归测试资产的唯一真相源仍是业务 Agent Workspace Git 中的
  `tests/test_*.py`；平台测试运行和发布条件以
  [业务 Agent Workspace 原生 pytest 测试资产实现方案](./engineering/业务AgentWorkspace原生pytest测试资产实现方案.md)
  为准。
- 本文出现的数据对象和字段名首先是领域概念，不构成现行 API 或存储 schema。当前公开契约
  以运行时 OpenAPI 为准；落地新增 schema 前必须先确认 Agent/SDK、Workspace Git 和现有
  AgentGov 对象没有持有或暴露同一事实。

### 0.2 治理对象与执行者

| 层级 | 被测或被治理对象 | 在 AgentGov 中的归属 |
| --- | --- | --- |
| L1 基座模型 | 固定版本的模型及推理参数 | 作为业务 Agent 版本的运行依赖或独立选型候选，不替代业务 Agent 生命周期 |
| L2 单业务 Agent | 模型、prompt、context、tool、memory、policy 和 Workspace 的组合 | 主要治理对象，归属到明确的业务 Agent、Git commit 和 Agent version |
| L3 多智能体工作流 | 多个业务 Agent、Subagent 或外部系统组成的协作链路 | 每次结果仍需归属到业务 Agent、版本、场景和执行证据；治理 Agent 不与业务 Agent 混同 |
| L4 运营闭环 | 运行、反馈、归因、优化、评估、发布和回滚 | 由 AgentGov 的 Runtime、Feedback Loop 和 Version Governance 承载 |

治理执行者是组合角色：

- Agent/SDK 提供会话、消息、tool call、Subagent 行为和 trace 的运行事实。
- AgentGov 后端负责确定性编排、权限校验、证据投影、评分执行和版本关联。
- 治理 Agent 负责需要模型判断的归因、方案和开放项分析，不生成后端已知的权威字段。
- 人工复核负责争议裁决、高风险动作确认和发布决策。
- 外部安全系统负责生产数据、业务权限、审批和真实处置结果。

### 0.2.1 业务 Agent、评测基准与平台发布测评

三者分别是被测对象、测量标准和发布裁决流程，不是三类并列的测试资产。其中“评测基准”
按稳定容器与不可变测量合同分为两层，因此下表展开为四行：

| 对象 | 含义 | 权威所有者 |
| --- | --- | --- |
| `BusinessAgentVersion` | 精确 Agent ID、Git commit、行为配置及运行依赖的组合，是被测对象 | Agent Registry + Workspace Git |
| `EvaluationBenchmark` | 稳定的命名基准与治理容器（`benchmark_id`），用于组织同一能力目标的历史测量合同 | 独立评测方或领域资产库；被测 Agent 无权改写 |
| `EvaluationProtocolRevision` | 基准下不可变的能力测量合同（`protocol_id + revision/digest`），冻结 case/corpus、Ground Truth、scorer、safety gate、采样/环境约束、阈值与退化容差 | 独立评测方或领域资产库；候选 Workspace 无权选择、读取 holdout 或改写契约 |
| 平台发布测评 | 平台在同一基准和运行条件下执行 baseline/candidate，并产生准入、拒绝或人工复核结论的治理动作 | AgentGov 后端规则、评测器与授权人员组合 |

`EvaluationBenchmark` 不承载某份可变试卷；`EvaluationProtocolRevision` 定义“测什么、如何判断、
在什么条件下可比”，冻结被测版本之外的 corpus、scorer、safety rules、Runtime/模型、工具、
推理参数、随机种子、采样次数、资源预算和环境约束。每次 execution 另记录实际环境指纹并校验
约束。脱离 benchmark ID 和精确 protocol revision
的分数不可直接比较，也不得称为“Agent 总能力分”。

```text
BusinessAgentVersion baseline + candidate
  + approved EvaluationBenchmark
  + immutable EvaluationProtocolRevision
        -> EvaluationExecution(s)
        -> Assessment（含 SafetyGate）
        -> EvaluationComparisonGroup
        -> EvaluationReviewDecision / ReleaseGateDecision
        -> release / improve / rollback
```

`EvaluationExecution` 是一次“精确 BusinessAgentVersion + benchmark ID + protocol revision + purpose +
environment fingerprint”的逻辑执行对象，并聚合协议规定的 `1..N` 个独立 sample。
Workspace pytest 的每个 sample 可由一个 `AgentTestRun` adapter 提供；后续动态场景或其他执行器
可使用其他 sample adapter，仍保持同一领域语义。

一个完成 execution 产生一份不可变 `Assessment`，只包含 Scorecard、Violation、SafetyGate、
采样稳定性和证据引用。`EvaluationComparisonGroup` 配对 baseline/candidate execution 与
assessment；`EvaluationReviewDecision` 和 `ReleaseGateDecision` 处于上层，不回写 Assessment。
P1 可以持久化这些对象的最小协议中立元数据和 `AgentTestRun` 引用，但不复制试卷正文或
Agent/SDK 运行事实，因此不是恢复旧 `TestDataset/EvalRun` 双轨。

### 0.3 资产归属

本能力与 AgentGov 长期口径一致，只定义三类一级资产：

| 一级资产 | 典型产物 | 权威归属 |
| --- | --- | --- |
| 数据/证据资产 | run、message、trace、evidence、score、violation、finding、review、release event | Agent/SDK 运行事实、AgentGov 投影或外部安全系统 |
| 方法论资产 | 能力模型、归因方法、评分规程、安全门槛、发布准入策略 | AgentGov Asset Registry 关联的受治理内容 |
| 执行资产 | prompt、skill、profile、playbook、Workspace 回归包、独立发布基准、evaluation case、场景包 | 业务 Agent Workspace Git、评测方受控资产库或明确的外部领域资产库 |

version/revision、digest/provenance、audit、scope/applicability 和 lifecycle 不是与三类资产并列的
“第四/第五类资产”，而是所有一级资产共同遵守的横切治理维度：

| 横切维度 | 必须回答 |
| --- | --- |
| Version / revision | 该资产的精确修订是什么，历史结果如何复现 |
| Provenance / digest | 资产来自哪里，内容是否未被替换 |
| Audit | 谁在何时创建、评审、修订、启用、发布或回滚 |
| Scope / applicability | 适用哪个 Agent、能力域、风险级别、Runtime 和组织边界 |
| Lifecycle | draft、approved、active、deprecated、archived 等阶段如何转移 |

评测语料、事实图和动态场景可以由领域资产库管理；AgentGov 只登记受控引用、revision、
digest、provenance、scope 和运行证据，不得为了“统一管理”复制出第二份 Workspace 测试正文、
第二份独立发布基准或第二套运行事实。

### 0.4 产品责任边界

AgentGov 负责：

- 注册和版本化治理业务 Agent；
- 记录或投影 Agent/SDK 提供的运行、消息、tool call 和 trace 事实；
- 关联评测协议、场景版本、评分结果、改进事项和发布证据；
- 承载反馈整理、归因分析、优化执行、测试发布和资产 Registry；
- 对高风险动作执行平台侧策略校验，并保留确定性审计记录。

外部安全系统负责：

- 告警、事件、资产、身份、情报、漏洞、工单等行业对象的权威数据；
- 生产系统访问控制、组织权限、审批、责任人和真实处置；
- Cyber Range、攻击仿真、日志重放和动态环境隔离；
- 数据分级、脱敏、授权、保留和销毁的业务责任；
- 面向安全运营人员的最终业务界面和争议裁决流程。

动态测试默认在隔离环境、模拟接口或安全沙箱执行。本文不授权 AgentGov 或业务 Agent
绕过外部系统的权限、审批和生产责任边界。

### 0.5 最小充分论证

| 检查项 | 结论 |
| --- | --- |
| 实际问题 | 传统知识题和单轮问答无法验证安全业务 Agent 的证据发现、工具使用、行动边界、协作连续性和版本稳定性 |
| 事实依据 | 网络安全任务依赖多源证据、受控工具、权限审批和可回放环境；AgentGov 已定义 Runtime、反馈闭环、Workspace 测试和版本治理边界 |
| 未选方案 | 不以大规模知识题库、单一综合分或数据库中的第二套测试正文作为主体系，因为它们不能证明受约束任务执行和版本回归 |
| 本文边界 | 定义目标能力和 MVP 验收，不预先声明具体路由、表、UI 按钮、状态机或存储实现 |
| 验收方式 | 以第 19 章场景证据为产品验收基础；具体实现还需通过 OpenAPI 契约、Workspace 测试、主流程测试和隔离环境验收 |
| 修订条件 | 权威标准、Agent Runtime、AgentGov 测试资产契约、外部安全系统边界或首批试点事实发生变化时重新评审 |

## 1. 文档目的

本文定义一套面向网络安全垂域智能体的测评工程需求。该工程不以建设传统知识题库为
最终目标，而是构建一套可持续演进、可验证、可复现、可审计的场景化测评体系，用于评价
基座模型、单业务 Agent、多智能体工作流及安全运营闭环在真实任务中的能力与风险。

本文主要回答以下问题：

1. 网络安全智能体应评测哪些能力；
2. 测试任务如何从权威标准和真实业务中产生；
3. 测试数据、标准答案和证据如何组织；
4. 如何观察智能体的调查过程、工具调用和行动轨迹；
5. 如何将权限、审批、误伤和提示注入风险纳入测评；
6. 如何将一次性测评升级为持续回归和版本治理体系。

## 2. 建设背景

多数大模型测评以选择题、问答题、代码题或人工偏好评价为主。这类测评能够评价模型的
知识、理解和部分推理能力，但难以反映网络安全运营业务 Agent 在真实环境中的核心能力，
例如：

- 是否能够从初始告警中识别调查方向；
- 是否能够主动调用日志、资产、身份、情报、EDR 等工具；
- 是否能够关联多源证据并还原攻击链；
- 是否能够区分事实、假设和未知信息；
- 是否能够发现初始告警之外的新证据；
- 是否能够在权限、审批和业务约束下安全行动；
- 是否能够避免误隔离、误封禁、错误归因和越权操作；
- 是否能够在模型、prompt、tool、rule 和数据变化后保持稳定。

因此，本能力拟建设一套以真实安全运营任务为中心的测评工程，将“答对问题”扩展为
“在约束环境中完成可验证任务”。

## 3. 建设目标

### 3.1 总体目标

建设一套面向网络安全智能体的证据驱动、工具可执行、风险约束型测评体系，为模型选型、
智能体研发、版本发布、能力优化和安全治理提供统一依据。

### 3.2 具体目标

1. 建立基于权威标准的安全运营能力模型；
2. 建立静态题、半动态任务和动态场景三类测试形态；
3. 建立以事实图和证据路径为核心的标准答案体系；
4. 建立覆盖推理摘要、工具、行动和交接的可观察轨迹采集机制；
5. 建立能力指标、可信指标、效率指标和安全门槛相结合的评分体系；
6. 建立场景、评测协议、业务 Agent 版本和结果的版本治理；
7. 建立失败样本进入改进事项、归因、优化、回归和发布的闭环；
8. 支持从单业务 Agent 测评逐步扩展到多智能体协作和安全运营闭环测评。

### 3.3 非目标

第一阶段不追求：

- 建设覆盖所有网络安全领域的超大规模通用榜单；
- 仅以选择题数量作为测评体系成熟度指标；
- 通过单一综合分数决定智能体是否可上线；
- 在无隔离环境下执行高风险真实攻击或生产处置；
- 替代现有 SOC、SIEM、SOAR、工单、知识库和安全测试平台；
- 用新的数据库测试集复制业务 Agent Workspace 中的可执行测试资产；
- 用本需求文档替代 OpenAPI、数据模型设计或运行态事实说明。

## 4. 设计原则

### 4.1 以标准定义任务

安全运营任务应优先从权威标准、岗位框架和业务流程中提取，避免仅依赖项目人员经验划分
能力。候选基线包括：

- NIST NICE：网络安全岗位、任务、知识和技能；
- NIST SP 800-61：事件响应活动和生命周期；
- FIRST CSIRT Services Framework：安全运营和事件响应服务；
- MITRE ATT&CK：攻击行为、战术和技术；
- MITRE D3FEND：防御技术和数字对象；
- OCSF：安全事件分类和字段语义；
- STIX 2.1：威胁对象、关系和事实表达；
- NIST AI RMF、TEVV：AI 风险和测试治理要求；
- OWASP Agentic Security 相关成果：提示注入、工具滥用、权限和记忆风险。

实施时必须在评测协议中固定实际采用的标准名称、版本、扩展和映射规则。标准升级不能静默
改变历史案例答案或评分结果。

### 4.2 以场景产生数据

测试数据不应主要依靠脱离上下文的人工问答生成，而应来自：

- 真实案例脱敏与重放；
- 攻击仿真产生的日志；
- 正常业务行为仿真；
- 故障、配置错误和数据质量异常；
- 专家构造的边界条件；
- 对抗性扰动和提示注入场景；
- 生产失败样本的治理化沉淀。

每条数据必须记录来源、授权、脱敏方式、版本、适用范围和污染风险。生产失败样本只有在
完成数据治理后才能进入长期回归资产。

### 4.3 以事实图保存答案

标准答案不应只保存一篇参考报告，而应保存机器可判定的事实、实体、关系、证据和动作约束。

事实图至少描述：

- 事件时间线；
- 主机、账号、进程、文件、网络、域名等实体；
- 实体之间的关系；
- 攻击链及 ATT&CK 映射；
- 关键证据与证据来源；
- 可接受结论、可接受差异和未知项；
- 推荐动作、允许动作、需审批动作和禁止动作。

### 4.4 以工具轨迹观察过程

测评不仅判断最终答案，还应采集 Agent/SDK 可观察的执行证据，包括：

- 输入上下文的版本与引用；
- 显式计划摘要和子任务；
- tool 名称、参数、返回引用、异常和耗时；
- 查询顺序和证据引用；
- 对外可见的中间结论及其修订；
- 人工审批请求；
- 最终动作和执行结果；
- token、时间、费用和预算结果。

不要求模型输出或系统保存隐藏思维链。过程评价只使用 Agent/SDK 原生暴露的消息、tool call、
Subagent 事件、结构化摘要和外部系统结果，后端不手解析 CLI transcript 或另建并行运行事实。

### 4.5 以安全边界约束行动

智能体完成任务不能以破坏安全边界为代价。以下问题纳入强约束：

- 未经授权调用工具；
- 超范围读取数据；
- 未经审批执行高风险动作；
- 对错误对象执行隔离、封禁或禁用；
- 被日志、邮件、网页或情报中的提示内容劫持；
- 泄露敏感信息；
- 在证据不足时过度处置；
- 隐瞒失败或伪造证据。

### 4.6 以回归测试推动持续改进

评测不是一次性验收，而应复用 AgentGov 的四阶段改进治理闭环：

```text
失败样本 / 人工反馈 / 安全违规
        ↓
改进事项与反馈整理
        ↓
归因分析
        ↓
优化执行
        ↓
测试发布：Workspace 回归测试、平台测试、发布或回滚
        ↓
Agent / version / 场景资产 Registry
```

模型、prompt、skill、rule、tool、policy 或数据调整是优化执行中的具体变更，不形成与改进事项
平行的用户主流程。

### 4.7 可见回归包与独立发布基准分层

业务 Agent 需要两类不同所有权的执行资产：

| 资产 | 用途 | 所有权与可见性 | 不能证明 |
| --- | --- | --- | --- |
| Workspace 可见回归包 | 单元测试、开发回归、历史缺陷保护和精确 commit 发布条件 | 属于业务 Agent Workspace Git，Agent 开发者可读、可改；按 per-Agent exact-commit lane 执行 | 独立能力提升、隐藏样本表现或线上业务效果 |
| evaluator-owned 发布基准 | 独立衡量能力和安全边界，支持 baseline/candidate 发布裁决 | 属于平台评测方或领域资产库；协议和规程可公开，holdout/Ground Truth 受控；候选无权改写 | 生产实际效果、长期漂移或外部审批已通过 |

平台发布测评不能仅运行候选 Workspace 自带试卷。开发集、公开测试和 holdout 必须在
revision、访问控制和 provenance 上分离；候选 Runtime 不得枚举、读取或将 holdout 包带出执行环境。
测评失败进入改进时，平台提供足以定位可修复语义的脱敏 `EvaluationFinding`，不暴露可被
定向优化的隐藏正文和答案。

## 5. 测评对象分层

### 5.1 L1：基座模型

评测模型在不调用外部工具时的基础能力：

- 网络安全知识；
- 标准理解；
- 日志理解；
- 基础推理；
- 结构化输出；
- 安全拒答与不确定性表达。

L1 结果用于模型选型或作为业务 Agent 版本的依赖证据，不单独替代 L2 业务 Agent 评测。

### 5.2 L2：单业务 Agent

评测“模型 + prompt + context + tool + memory + policy + Workspace”的整体能力：

- 任务规划；
- 多步调查；
- 工具调用；
- 证据关联；
- 结论形成；
- 行动决策；
- 报告输出。

每次结果必须归属到明确的 `agent_id`、Git commit、Agent version、评测协议和场景版本。

### 5.3 L3：多智能体工作流

评测多个业务 Agent、Subagent 或外部子系统之间的协作能力：

- 任务拆分；
- 状态传递；
- 证据共享；
- 冲突处理；
- 重复查询控制；
- 人工介入；
- 会话连续与事实连续。

业务 Agent 是被治理对象；Subagent 是业务 Agent 内部的能力组织方式；治理 Agent 是评测和
改进闭环的执行者。三者的身份、版本、权限和证据不得混为一体。

### 5.4 L4：运营闭环

评测系统长期运行和持续改进能力：

- 反馈采集与归属；
- 失败归因；
- 优化执行；
- 回归测试；
- 灰度发布；
- 版本比较；
- 回滚恢复；
- 能力资产沉淀。

## 6. 能力模型

第一版能力模型划分为七个领域。

### 6.1 安全数据理解与标准化

- 原始日志字段识别；
- schema 映射；
- OCSF 分类和字段校验；
- OCSF 到 STIX 映射；
- 时间、实体、方向和类型一致性校验；
- 缺失字段、冲突字段和异常值发现；
- 数据血缘和证据引用。

### 6.2 威胁情报分析

- IOC 提取和标准化；
- 威胁实体识别；
- 情报可信度判断；
- ATT&CK 映射；
- 情报与内部资产、日志和事件关联；
- 情报时效性判断；
- 检测建议生成。

### 6.3 检测规则开发与验证

- 从攻击行为或情报生成规则；
- Sigma、YARA、KQL、ES 查询等规则编写；
- schema 适配；
- 规则语法校验；
- 攻击样本检出；
- 正常样本误报测试；
- 规则解释和适用范围说明。

### 6.4 告警分诊与研判

- 告警去重与聚合；
- 真阳性、误报、存疑判断；
- 告警优先级；
- 证据充分性判断；
- 缺失证据识别；
- 下一步调查建议；
- 置信度表达。

### 6.5 事件调查与威胁狩猎

- 初始调查计划；
- 多源日志查询；
- 进程树、网络、文件、账号和主机关联；
- 时间线还原；
- 新证据发现；
- 影响范围识别；
- 攻击链还原；
- 假设验证与反证；
- 调查停止条件。

### 6.6 响应处置与风险控制

- 处置目标识别；
- 动作选择；
- 业务影响评估；
- 最小化处置；
- 审批请求；
- 隔离、阻断、账号控制和取证；
- 动作结果验证；
- 失败回滚；
- 误伤控制。

### 6.7 报告、交接与持续改进

- 事实、判断和建议分离；
- 证据引用；
- 事件摘要和时间线；
- 风险与未知项说明；
- 面向不同角色输出；
- 向其他智能体或人工交接；
- 失败样本结构化；
- 回归测试设计和改进事项生成。

## 7. 测试形态

### 7.1 静态测试

输入固定，不能调用外部工具。

适用于：

- 安全知识；
- 标准理解；
- 单条日志或告警分析；
- 结构化输出；
- 数据标准化审查；
- 安全拒答和提示注入识别。

### 7.2 半动态测试

提供固定数据包和受控查询接口，智能体可自主选择查询对象和顺序。

适用于：

- 告警调查；
- 多源证据关联；
- 攻击链还原；
- 规则生成与离线验证；
- 资产和账号影响分析。

### 7.3 动态场景测试

在隔离环境中运行攻击、正常业务和响应动作，环境状态会随智能体操作变化。

适用于：

- 威胁狩猎；
- 事件响应；
- 多智能体协作；
- 权限和审批；
- 行动校准；
- 对抗性安全测试。

动态环境的状态真相源属于 Cyber Range、模拟器或外部安全系统。AgentGov 保存关联标识、
版本、投影结果和审计证据，不以自建副本取代环境权威状态。

## 8. 场景设计要求

### 8.1 场景来源

每个场景标记来源类型：

- 真实案例脱敏；
- 攻击仿真；
- 专家原创；
- 生产失败样本；
- 标准规则派生；
- 模型生成后专家审核。

### 8.2 场景组成

一个完整场景至少包含：

1. 场景目标；
2. 初始观察；
3. 环境状态及权威来源；
4. 可访问数据；
5. 可调用工具；
6. 权限与审批约束；
7. Ground Truth 事实图；
8. 关键证据路径；
9. 可接受动作和禁止动作；
10. 评分规则；
11. 停止条件；
12. 版本、来源和数据授权信息。

### 8.3 样本构成

测试集同时包含：

- 真阳性案例；
- 误报案例；
- 证据不足案例；
- 多阶段攻击案例；
- 内部人员或合法运维行为；
- 数据缺失或字段错误案例；
- 多个合理调查路径案例；
- 高价值资产和高风险动作案例；
- 提示注入、工具劫持和越权诱导案例；
- 需要人工确认的案例。

### 8.4 难度分级

- D1：单一事实、单一数据源、答案明确；
- D2：两至三步关联，存在少量干扰；
- D3：多源证据、多跳推理，存在正常行为干扰；
- D4：信息不完整，需要假设验证和反证；
- D5：动态环境、多智能体协作、高风险动作和对抗性输入。

难度是场景元数据，不直接等价为业务 Agent 生命周期状态。

## 9. 事实图与标准答案

### 9.1 事实图对象

事实图至少支持表达以下领域对象：

- Alert；
- Finding；
- Incident；
- Host；
- UserAccount；
- Process；
- File；
- Directory；
- NetworkTraffic；
- IP；
- Domain；
- Vulnerability；
- ThreatActor；
- Indicator；
- Action；
- Evidence；
- Approval；
- ToolCall。

这些对象属于安全领域事实模型，不自动成为 AgentGov 的 ORM、API DTO 或持久化表。落地时
优先引用外部系统对象和证据，只有缺少权威来源且确有平台治理需要时才新增平台投影。

### 9.2 事实图关系

典型关系包括：

- process spawned process；
- process executed file；
- process connected to domain/IP；
- user logged into host；
- alert indicates behavior；
- evidence supports finding；
- finding belongs to incident；
- action targets entity；
- action requires approval；
- technique mitigated by action。

### 9.3 答案类型

标准答案区分：

- 必须命中的事实；
- 可选但有价值的事实；
- 可接受的等价表达；
- 不应出现的错误事实；
- 尚未确定的未知事实；
- 合法的多路径答案；
- 安全动作白名单；
- 条件允许动作；
- 禁止动作。

### 9.4 证据要求

结论必须关联证据。系统支持判断：

- 引用是否存在；
- 引用是否相关；
- 引用能否支持结论；
- 引用是否被篡改；
- 是否遗漏关键证据；
- 是否将假设伪装成事实。

证据引用应尽量指向外部权威对象或不可变内容摘要；报告中的自然语言复述不能取代原始证据。

## 10. 工具与轨迹观测

### 10.1 工具分类

- 查询类：日志、资产、身份、情报、漏洞、进程树；
- 分析类：解码、哈希、规则校验、沙箱、图查询；
- 写入类：工单、事件、标签、知识库；
- 处置类：隔离、封禁、禁用、终止进程；
- 协作类：委派 Subagent、请求人工、发送交接信息。

### 10.2 轨迹采集

每次工具调用至少能够关联以下语义：

```yaml
call_id: 唯一标识
case_id: 测试案例
agent_id: 业务 Agent
agent_version: 业务 Agent 版本
tool_name: 工具名称
arguments: 调用参数或受控摘要
policy_decision: 允许/拒绝/需审批
start_time: 开始时间
end_time: 结束时间
result_summary: 返回摘要
result_ref: 原始结果引用
error: 异常信息
evidence_ids: 关联证据
parent_call_id: 上游调用
```

以上是观测语义，不是预先确认的 HTTP 或数据库 schema。`call_id`、`case_id`、`agent_id`、
时间、策略决策、权限范围和 provenance 等字段由 SDK、后端或外部系统生成并覆盖，不能要求
业务 Agent 或治理 Agent 在输出中自述为权威值。敏感参数和结果按数据分级保存，摘要不能成为
绕过访问控制的副本。

### 10.3 过程评价

过程评价包括：

- 是否选择必要工具；
- 是否使用错误工具；
- 查询顺序是否合理；
- 是否进行无意义重复查询；
- 是否及时修正错误假设；
- 是否在关键信息缺失时停止并请求人工；
- 是否在预算范围内完成任务。

不要求所有优秀智能体使用完全相同的轨迹。评分允许多条合理调查路径，并避免把隐藏思维链、
特定模型措辞或固定工具顺序当作正确性的唯一依据。

## 11. 评分体系

### 11.1 评分原则

1. 分项优先，不以单一总分替代能力画像；
2. 最终结果和执行过程同时评分；
3. 正确结论必须有证据支撑；
4. 漏报、误报和误处置分别计量；
5. 安全违规采用门槛或一票否决；
6. 允许合理的多路径和等价答案；
7. 开放任务采用确定性校验、规则评分、治理 Agent 辅助分析和人工裁决结合；
8. 评分器、规则、阈值和人工修订都必须版本化并可追溯。

### 11.2 核心能力指标

- 研判准确率；
- 关键事实召回率；
- 证据精确率；
- 证据覆盖率；
- 新证据发现率；
- 攻击链完整度；
- 影响范围识别准确率；
- 工具选择正确率；
- 处置动作准确率；
- 交接信息完整度；
- 报告事实一致性。

### 11.3 可信与安全指标

- 幻觉事实率；
- 无证据结论率；
- 越权调用率；
- 未审批高风险动作数；
- 误隔离、误封禁和误禁用数；
- 提示注入成功率；
- 敏感数据泄露次数；
- 风险置信度校准；
- 失败承认率；
- 可审计性。

### 11.4 效率指标

- 完成时间；
- 工具调用次数；
- 无效调用次数；
- token 消耗；
- 模型调用次数；
- 运行成本；
- 首次发现关键证据时间；
- 首次正确处置时间。

### 11.5 评分结果

每次测评输出：

1. 分领域得分；
2. 分任务得分；
3. 安全门槛结果；
4. 失败案例列表；
5. 证据与轨迹详情；
6. 与修复前版本或指定历史版本的差异；
7. 稳定性和多次运行方差；
8. 发布条件判断及依据。

## 12. 安全门槛

以下行为设置为一票否决或强制人工复核：

- 未经批准隔离生产关键主机；
- 对错误账号执行禁用；
- 阻断正常核心业务域名或地址；
- 超出案件范围读取敏感数据；
- 执行测试环境未授权的破坏性命令；
- 因提示注入改变任务目标或安全策略；
- 伪造工具结果、证据或审批记录；
- 隐藏执行失败；
- 绕过人工介入点；
- 将不确定事实作为确定结论推动高风险行动。

安全门槛结果独立于综合分。例如，综合能力得分较高但发生一次严重越权处置，最终仍判定
不通过。具体门槛、严重度、审批主体和恢复条件必须在评测协议中固定，不能由被测 Agent
自行解释。

## 13. 测评执行流程

```text
选择被测业务 Agent、baseline/candidate Git commit 和版本
        ↓
选择已批准的评测基准 revision、场景版本和运行协议
        ↓
初始化隔离环境与数据
        ↓
分别生成 baseline/candidate EvaluationExecution 并采集 SDK/外部系统证据
        ↓
确定性评分与事实图比对
        ↓
治理 Agent 辅助评分或专家裁决开放项
        ↓
执行安全门槛检查
        ↓
校验可比指纹并生成 baseline/candidate 差异报告
        ↓
失败 EvaluationFinding 创建或关联改进事项
```

### 13.1 评测协议必须固定

- 模型名称和具体版本；
- system prompt、Workspace 和 Agent 配置版本；
- 工具列表、权限和外部 endpoint 版本；
- 测试集、场景和 Ground Truth 版本；
- 温度、最大输出长度等推理参数；
- 最大步骤、时间和费用预算；
- 是否允许重试；
- 人工介入规则；
- 评分器、规则和标准版本；
- 评分重复次数与 Agent 独立执行采样次数，两者不共用一个模糊 `repeat_count`；
- baseline/candidate 可比指纹、各分项退化容差和 `incomparable` 处理；
- 运行时间、随机种子和环境信息。

协议内容包含敏感 endpoint、header 或凭据时，只保存受控引用或密文，不进入项目源码仓库、
公开文档、日志摘要或导出报告。

同一已捕获输出的重复评分只证明 scorer determinism；同一 BusinessAgentVersion 在新 `run_id` 上的多次
独立执行才用于估计平均值、最小值、方差和安全事件。发布报告必须分开展示这两类证据。

## 14. 回归测试与持续改进

### 14.1 回归测试组合

- 核心能力基线场景；
- 历史失败样本；
- 高风险安全门槛场景；
- 当前版本变更影响场景；
- 随机抽样稳定性场景；
- 新增场景候选。

领域案例和场景可以组织为版本化场景包；可执行的业务 Agent 回归断言仍物化到该 Agent
Workspace Git 的 `tests/test_*.py`。`RegressionTestDesign` 只是候选测试语义，
`AgentTestRun` 是精确 commit 上的平台运行证据，二者都不能由新的数据库测试正文替代。

### 14.2 触发条件

以下变化触发相应范围的回归测试：

- 更换模型或模型版本；
- 修改 prompt、rule 或 skill；
- 新增或修改 tool；
- 修改权限策略；
- 修改数据 schema 或标准映射；
- 修改知识库；
- 修改多智能体流程；
- 发现生产失败或安全事故；
- 新增重要攻击技术或业务场景。

变更影响选择可以用于内循环，但发布前必须满足业务 Agent 的完整 Workspace 测试和对应高风险
安全场景门禁，不能用一次选择性通过替代完整发布证据。

### 14.3 发布门禁

发布前至少满足：

- 核心场景无显著退化；
- 高风险安全集全部通过；
- 新增能力达到最低阈值；
- baseline/candidate 使用同一 benchmark ID 与精确 protocol revision，因而共享同一
  Runtime/模型/工具/环境指纹和采样规则；
- 任一指纹不同时结果标记为 `incomparable` 并成对重跑，不得用不可比高分放行；
- 当前 candidate 的完整 Workspace 回归与独立发布测评同时通过；
- 成本和时延在预算范围内；
- 失败案例已有明确归因；
- 评测报告、Agent commit 和版本记录完整；
- 支持灰度和回滚；
- 平台发布条件与外部业务系统审批都已满足。

## 15. 产品功能需求

本章描述目标能力分区，不直接映射为 UI 菜单、按钮、API 路由、job type 或持久化状态。
具体产品设计必须从用户旅程、业务产物、动作副作用和审计记录反推最小入口。

### 15.1 基准与标准管理

- 管理权威标准和能力映射；
- 管理能力领域、任务和子任务；
- 分开管理稳定 `EvaluationBenchmark` 与不可变 `EvaluationProtocolRevision`；
- 管理测评依据、适用范围、owner、修订链和废弃条件；
- 正式 protocol revision 由评测方独立评审，不接受被测 Agent 或候选 Workspace 更改；
- 支持能力树浏览和变更记录；
- 标准升级时保留历史协议和评分可复现性。

### 15.2 测评语料与案例管理

- 创建、导入、审核和发布领域案例；
- 区分训练、开发、公开测试和隐藏测试用途；
- 管理样本标签、难度、来源、授权和 provenance；
- 支持数据脱敏、污染检查和重复检查；
- 支持案例版本和废弃状态；
- 只登记 Workspace 测试资产的路径、commit、摘要和运行证据，不复制测试正文。

### 15.3 场景管理

- 场景模板和版本；
- 环境初始化脚本或外部环境引用；
- 攻击和正常行为仿真；
- tool、权限和审批配置；
- Ground Truth 事实图配置；
- 场景验证、发布和退役。

### 15.4 测评执行管理

- 选择业务 Agent、精确 commit、场景和协议；
- 批量运行；
- 并发和资源控制；
- 中止、重试和恢复；
- 运行状态和异常监控；
- 隔离环境的初始化、清理和证据关联。

### 15.5 评分与裁决

- 规则评分；
- schema 校验；
- 事实图比对；
- 代码或查询执行验证；
- 治理 Agent 交叉分析；
- 专家争议裁决；
- 评分结果修订留痕。

### 15.6 结果分析

- 综合概览；
- 能力雷达和分项趋势；
- 失败模式聚类；
- 版本对比；
- 模型、prompt、tool 和 policy 对比；
- 成本与性能分析；
- 安全违规详情；
- 从分数下钻到场景、事实、证据、轨迹和协议。

### 15.7 改进闭环

- 将失败样本、人工反馈或安全违规创建或关联到改进事项；
- 在反馈整理阶段关联运行轨迹、证据和评分；
- 在归因分析阶段生成并确认归因结果；
- 在优化执行阶段生成方案、审查 Diff 并应用受控变更；
- 在测试发布阶段生成 Workspace 测试候选、运行完整测试并检查发布条件；
- 关联 Agent commit、change set、release、rollback 和资产 Registry。

“生成归因分析”“生成优化方案”“自动执行优化”“执行回归测试”等用户动作必须产生对应
业务产物并调用真实业务 API；生命周期推进只能作为业务动作的副作用。

### 15.8 产品信息架构与入口分工

下列分工是长期产品契约，不表示当前前端菜单已实现：

| 入口 | 主要用户任务 | 信息所有权 |
| --- | --- | --- |
| 业务 Agent 详情 → 测评 | 查看单个 Agent 的基准适用性、baseline/candidate 比较、发布准入、历史趋势和线上效果 | 长期单 Agent 测评主入口 |
| 独立测评中心 | 管理基准、隐藏集、跨 Agent campaign、专家评审队列、周期再评估和组合风险 | 评测方和治理运营视图；不编辑业务 Agent Workspace |
| 资产复利 → 测试资产 | 查看 Workspace 测试源码、suite、精确 commit 运行历史和证据详情 | 业务 Agent 可见回归包；不管理 holdout 正文 |
| Asset Registry | 追溯 BusinessAgentVersion、benchmark、execution、finding、improvement、change set 和 release 关系 | 只存引用、digest、scope、provenance 和审计，不复制正文 |

首个具备 holdout 与 baseline/candidate comparison 的窄切片就应直接交付“业务 Agent 详情 → 测评”
主入口；现有测试运行详情只承担单个 `AgentTestRun` sample 的 evidence drill-down。组件以
`agent_id + evaluation execution/comparison` 为输入，不依赖测试资产页的局部 state。出现第二个
benchmark/protocol、跨 Agent campaign、持续隐藏集运营或专家队列时，应启用独立测评中心；
单个受控 holdout 不单独触发组合级中心。

## 16. 核心数据对象与所有权

本章只定义领域概念和所有权，不要求逐项新建表或 schema。实现设计必须先复用 Agent/SDK
事实、现有 AgentGov typed model、Workspace Git 和外部系统对象，再决定是否需要新的边界投影。

### 16.1 领域定义与场景资产

| 概念 | 作用 | 权威所有者 |
| --- | --- | --- |
| Standard | 标准及版本 | 标准 Registry 或领域资产库 |
| Capability | 能力领域和层级 | AgentGov 方法论资产 |
| TaskDefinition | 可评测任务定义 | 场景包或领域资产库 |
| EvaluationBenchmark | 稳定命名的能力测量与治理容器；不是试卷或一次运行 | 评测方或领域资产库；AgentGov 保存 `benchmark_id` 与 scope |
| EvaluationProtocolRevision | 基准下不可变的测量合同，冻结 corpus、Ground Truth、scorer、safety gate、采样与环境约束 | 评测方受控资产库；AgentGov 保存精确 revision/digest 引用 |
| EvaluationCorpus | 版本化案例集合，不等同于已删除的数据库 `TestDataset` | 评测方或领域资产库；AgentGov 保存受控引用 |
| EvaluationCase | 输入、答案、证据、评分和安全约束；明确区分可见回归变体与 holdout | 可见回归归业务 Agent Workspace；正式 holdout 归评测方受控资产库 |
| SecurityScenario | 动态环境、初始状态和停止条件 | Cyber Range 或场景资产库 |
| GroundTruthGraph | 事实、关系、证据和允许动作 | 场景资产库 |
| ToolDefinition | 工具能力和风险分类 | 业务 Agent Workspace 与外部工具 Registry |
| SecurityPolicy | 权限、审批和禁止动作 | 外部安全系统；AgentGov 保存执行决策证据 |
| EvaluationProtocolRef | 对精确 `protocol_id + revision + content_digest` 的受控引用 | AgentGov backend-owned 运行投影 |

### 16.2 运行与评分证据

| 概念 | 作用 | 权威所有者 |
| --- | --- | --- |
| BusinessAgent / BusinessAgentVersion | 被测业务 Agent 和版本 | AgentGov Agent Registry 与 Workspace Git |
| Session / Message / ToolCall / Subagent event | 原始运行事实 | Agent/SDK 与外部工具系统 |
| TraceSummary / Evidence | 面向评测和治理的证据投影 | AgentGov，不复制底层事实 |
| EvaluationExecution | 一次精确 BusinessAgentVersion、protocol revision、Runtime/模型/工具/环境的逻辑执行，聚合 `1..N` 个 sample；不是旧 `EvalRun` 兼容入口 | 协议中立对象；Workspace pytest sample 可由 `AgentTestRun` adapter 提供 |
| Assessment | 绑定 EvaluationExecution 的不可变 Scorecard、Violation、SafetyGate、采样稳定性和证据引用 | 确定性评分器与后端规则生成的 typed 投影；不包含 comparison、人工 review 或 release gate |
| EvaluationComparisonGroup | 在兼容协议和环境下关联 baseline/candidate executions | AgentGov backend-owned 关系与差异投影 |
| EvaluationFinding | 可脱敏下钻的失败、退化或安全违规证据单元 | AgentGov 从 Assessment 派生；不复制 holdout 正文 |
| EvaluationReviewDecision | 人工复核、争议裁决和例外处理，不回写 Assessment | 授权用户或外部审批系统 |
| ReleaseGateDecision | 组合当前回归、comparison、SafetyGate、必要 review 与外部审批引用形成发布裁决 | AgentGov backend-owned 门禁规则与授权审批事实 |

### 16.3 改进、测试与发布对象

| 当前统一对象 | 作用 |
| --- | --- |
| ImprovementItem | 承接失败样本、反馈、归因、优化、测试和发布的治理单元 |
| RegressionTestDesign | 治理 Agent 生成、用户确认的回归测试语义候选 |
| WorkspaceTestFile | 业务 Agent Git 中的可执行测试资产唯一真相源 |
| AgentTestRun | 固定 pytest 命令在精确 commit 上产生的平台测试证据 |
| EvaluationFindingImprovementLink | 多对多关联 EvaluationFinding 与 ImprovementItem；一个事项可汇总多次 execution，一个 finding 也可显式关联多个改进责任 |
| AgentChangeSet | 同一业务 Agent 的待发布变更 |
| Release / rollback | 发布、恢复、回滚和版本审计 |
| OnlineOutcome | 关联 `Release / BusinessAgentVersion` 的外部线上业务结果，至少保存 `source_ref`、`observation_window`、`metric_definition`、scope 和 provenance；不反向改写发布时 Assessment。外部业务系统是事实源，AgentGov 只保存受控引用或投影 |
| AssetRecord / Asset Registry | 关联数据/证据、方法论和执行三类一级资产，把 version、provenance、audit、scope 和 lifecycle 作为横切维度；不复制 Workspace 或 holdout 正文 |

## 17. 非功能需求

### 17.1 可复现性

同一业务 Agent commit、同一评测协议和同一场景版本能够重复运行，并完整记录随机种子、
环境、依赖和评分器版本。无法固定的外部状态必须显式标注并进入结果解释。

### 17.2 可审计性

所有数据修改、评分修订、人工裁决、权限决策、发布和回滚操作留痕。审计字段由后端或
外部权威系统生成，不接受 Agent 输出覆盖。

### 17.3 安全隔离

动态测试和处置动作在隔离环境、模拟接口或安全沙箱中执行，禁止直接影响未经授权的生产环境。

### 17.4 可扩展性

支持新增安全领域、数据源、tool、评分器、Agent Runtime 和多智能体框架，同时保持
业务 Agent、评测协议和证据归属清晰。

### 17.5 可解释性

每个分数能够下钻到案例、事实、证据、轨迹和评分规则；开放项同时展示确定性证据、模型分析
和人工修订边界。

### 17.6 数据安全

支持数据分级、脱敏、访问控制、加密、保留周期和销毁机制。报告、trace 摘要和调试界面都不能
成为绕过原始数据权限的副本。

### 17.7 性能

支持批量任务排队、并发运行、资源配额、取消和失败重试。具体吞吐、时延和成本指标在 MVP
实施阶段按资源与风险等级确定，并写入可版本化评测协议。

## 18. MVP 范围

第一阶段采用“一静一动”两条试点线。

### 18.1 试点一：安全数据标准化审查

范围：

- 原始日志到 OCSF；
- OCSF 到 STIX；
- 字段、分类、类型和关系审查；
- 问题清单、标准依据和修复建议；
- 自动 schema 校验和事实比对。

建议样本：30 至 50 个案例。

重点验证：

- 能力模型是否可落地；
- Ground Truth 是否可机器判定；
- 评分器是否稳定；
- 失败样本能否进入改进事项和回归闭环。

### 18.2 试点二：告警研判与多跳调查

范围：

- `process_activity`；
- `network_activity`；
- `detection_finding`；
- 资产和账号上下文；
- 受控日志查询工具；
- 事件判断、证据发现、攻击链和处置建议。

建议样本：20 至 30 个案例。

重点验证：

- Agent/SDK 与外部工具轨迹是否完整；
- 是否能够发现初始告警之外的新证据；
- 是否能够区分事实和假设；
- 是否遵守人工介入点和安全边界。

### 18.3 MVP 不包含

- 完整 Cyber Range；
- 大规模勒索软件全流程演练；
- 生产系统真实自动处置；
- 大规模公开排行榜；
- 跨组织数据共享；
- 未经独立设计评审的新通用协作工作流。

## 19. MVP 验收标准

### 19.1 功能验收

- 支持创建和版本化管理领域案例或其受控引用；
- 支持配置 Ground Truth 事实和证据；
- 支持至少一种业务 Agent Runtime 接入；
- 支持受控工具调用和轨迹采集；
- 支持规则评分、事实比对和人工复核；
- 支持生成分项测评报告；
- 支持失败样本转为或关联改进事项；
- 支持 Workspace 批量回归和版本对比。

### 19.2 数据验收

- 形成不少于 50 个高质量案例；
- 每个案例具备来源、授权、目标、输入、答案、证据和评分规则；
- 核心案例经至少两名安全人员独立复核并记录争议处理；
- 隐藏测试集与开发调试集分离；
- 样本不存在明显重复、泄漏和歧义；
- 敏感数据不进入项目源码仓库、公开文档和非授权日志。

### 19.3 质量验收

- 确定性评分可重复；
- 同一运行结果重复评分一致；
- 人工争议案例有裁决流程；
- 所有高风险动作均经过策略拦截或审批；
- 测评结果能够下钻到证据和轨迹；
- 新版本能够与指定历史版本进行差异比较；
- 空态、成功态、评分失败详情和重试入口均有场景证据；
- 发布判断能够关联精确业务 Agent commit、评测协议、测试运行和外部审批。

## 20. 建设阶段

以下是本能力的建设阶段，不是改进治理工作台的用户可见四阶段。

### 建设阶段一：成果调研与能力建模

- 建立权威成果清单及版本；
- 建立标准、岗位、任务和能力映射；
- 明确测评对象分层；
- 输出能力模型 V1.0。

### 建设阶段二：数据和评分最小闭环

- 建设标准化审查测试集；
- 建设事实图和证据模型；
- 接入确定性评分器；
- 跑通单次测评和报告。

### 建设阶段三：工具化调查任务

- 建设告警研判和多跳调查场景；
- 接入受控查询工具；
- 采集 SDK 与外部工具轨迹；
- 引入调查深度和新证据评分。

### 建设阶段四：安全动作与人机协作

- 接入模拟处置工具；
- 建设权限和审批策略；
- 引入提示注入和误处置测试；
- 评测人工介入和交接。

### 建设阶段五：多智能体与闭环评测

- 引入有明确业务所有者的多智能体任务；
- 建设共享状态和事实连续测试；
- 建立改进、回归、灰度和回滚闭环；
- 形成组织级测评基线。

## 21. 风险与应对

### 21.1 测评范围过大

风险：第一版试图覆盖完整 SOC，导致无法形成高质量样本和评分器。

应对：优先选择标准化审查和告警调查两个可验证场景。

### 21.2 标准答案过于主观

风险：专家参考答案无法自动评分，争议多。

应对：采用事实图、证据路径、动作白名单、可接受差异和独立复核。

### 21.3 数据污染

风险：公开样本进入模型训练或被针对性优化。

应对：划分公开集、开发集和隐藏测试集，持续生成新场景并保留 provenance。

### 21.4 模型辅助裁判偏差

风险：治理 Agent 或其他模型偏爱冗长表达、特定模型风格或自身生成结果。

应对：优先确定性评分；模型只分析开放项；采用交叉分析、盲化输入和人工抽检。

### 21.5 轨迹评分过度僵化

风险：要求固定调查路径，误伤合理的新策略。

应对：以关键证据、结果和安全边界为主，允许多条有效路径，不评价隐藏思维链。

### 21.6 高分但不安全

风险：能力分数掩盖严重越权或误处置。

应对：安全门槛独立判定，重大违规一票否决。

### 21.7 测评不能代表生产

风险：测试环境过于理想化。

应对：逐步引入噪声、数据缺失、业务约束、真实失败样本和生产影子评测；生产影子评测仍
不得获得未授权写权限。

### 21.8 权威事实重复

风险：平台复制外部安全对象、SDK trace 或 Workspace 测试正文，形成多套真相源。

应对：优先保存引用、摘要、digest 和 provenance；新增存储前证明现有权威源不能满足治理需要。

### 21.9 目标方案被误读为当前能力

风险：概念对象或功能分区被直接当作现行 API、数据库表、菜单或状态机。

应对：实现前完成字段所有权、动作副作用、OpenAPI、数据迁移和测试矩阵评审；当前能力只以
运行时 OpenAPI、代码和实现基线文档为准。

## 22. 实施前决策门

以下问题必须在对应能力进入实现设计前形成可追溯决策，不能靠隐式默认或新增兼容层绕过：

1. 第一阶段分别对 L1 基座模型和 L2 业务 Agent 提供哪些结果，发布门禁以哪个层级为准；
2. 能力模型以安全运营流程为主线还是以 NICE 岗位为主线，二者如何版本化映射；
3. Ground Truth 直接采用 STIX 扩展还是独立测评模型，权威对象和扩展边界是什么；
4. `detection_finding` 是待核验对象还是已确认事实；
5. 第一批工具使用真实 API、mock API 还是离线数据查询，各自的证据可信度如何标记；
6. 哪些动作一票否决，哪些动作扣分或强制人工复核；
7. 公开、开发和隐藏测试集的比例及污染控制；
8. 专家复核和争议裁决的最低人员、独立性和审计要求；
9. 是否需要组织内部排行榜，以及排行榜不能替代哪些发布门禁；
10. 与 AgentGov、Langfuse、SOC/SIEM/SOAR、工单、知识库、场景资产库和测试平台的事实所有权及集成边界；
11. 引入动态场景、人工 runner 或跨 Agent campaign 时，如何在保留最小协议中立
    `EvaluationExecution`/`Assessment`/comparison 记录的前提下扩展 sample adapter 和公开 API，
    并保持 Workspace、评测方资产库和 Agent/SDK 事实各自的单一真相源，不恢复旧
    `TestDataset/EvalRun` 双轨；
12. 动态场景的隔离级别、清理证明、生产影子评测权限和事故停止条件。

## 23. 一句话定位

本能力不是建设一套只考网络安全知识的题库，而是建设一套能够回答以下问题的测评工程：

> 业务 Agent 是否能够依据标准理解任务，在真实或仿真的安全场景中主动获取证据，形成可追溯判断，在权限和风险边界内采取行动，并通过持续回归不断提高能力与可靠性。
